# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository. It holds the rules and traps that still apply. The history of how each was found is in git, the issues and `CHANGELOG.md`, so it does not belong here.

## Working Principles

### Principle of least exposure
Only expose API fields and serialization groups when they are concretely needed by a consumer. Add serialization only when there is a real, tested requirement for it.

### No code comments
Do not write explanatory comments in code. The behaviour and the reason for a change belong in the test that covers it — a named PHPUnit test method — not in prose beside the implementation. Remove narrative comments from any file you touch. Keep file licence headers and type-carrying annotations (`@var`, `@param`, `@return`, `@template`) that static analysis or the framework needs.

### Public readability is reachability from a live route
> *"If a user should be able to load that component because the route that it is part of exists and is available now to the public. Simple as that in the theory of it."* — Daniel

A resource is publicly readable **if and only if** it is reachable from a Route that **exists** and is **live now**. Test every security decision against that rule, not against what the voters currently do. "Live now" is `RouteVoter`'s job (it folds in `liveAt` and `route_security`), so `is_granted('read_route', $route)` is the complete answer for one route; reachability is the question of *which* routes reach a resource.

Both directions are enforced (#225): a routeless page with a live routed descendant **is** public; a page nothing routes to is **not**, however it is reached in the object graph.

### Abstention is a decision, not a neutral one
An abstaining voter has not "stayed out of it": under `AffirmativeStrategy`, all-abstain is a denial (`allowIfAllAbstainDecisions` defaults to `false`). This has caused four bugs:

- `RouteVoter::supports()` returned false when `route_security` was unconfigured, so every routed page 401'd for everyone (#224).
- `ComponentVoter` granted when all three sub-votes abstained, so a component in an unrouted page was public (#225).
- `SiteConfigParameterVoter::supports()` needs a `SiteConfigParameter`. A plain `security:` on a `Post` runs with no object, so every voter abstains and even admins are denied. Use `securityPostDenormalize:` (#232).
- `voteByPageTemplate` abstains only for a `Page` with no page data at all, so a routeless *template* page and a routeless *plain* page are not interchangeable in a regression test (#225).

**Before relying on a voter, state what happens when it abstains**, and write the test that pins it. `supports()` returning false is abstention, not denial; never put a configuration check there.

### TDD process
1. Explain what we're about to do and why, with a proposed test (a functional or unit PHPUnit test)
2. Agree on whether the test is correct (Daniel is the author and has deep system knowledge — expect discussion)
3. Write or adjust the test, watch it fail, then write the code to make it pass
4. Keep CLAUDE.md current throughout, but record **rules and traps**, not the story of the change
5. Add a line to `CHANGELOG.md` under **Unreleased** in the same PR (see below)
6. For a user-facing change, raise an issue on `components-web-app/docs` describing what to document, linking the bundle PR or issue

### Changelog and releases
`CHANGELOG.md` is maintained continuously and is the source of every release's notes.

- **Every PR that changes behaviour, config, dependencies or tooling adds a line under `## Unreleased`**, in the matching `### Breaking` / `### Added` / `### Changed` / `### Fixed` / `### Tooling` group. One short line, ending with a link to the PR (`[#123](https://github.com/components-web-app/api-components-bundle/pull/123)`), or to the commit for a direct push.
- **Tagging a release:** in the release commit, rename `## Unreleased` to `## [<tag>](https://github.com/components-web-app/api-components-bundle/compare/<previous-tag>...<tag>) - YYYY-MM-DD` and add a fresh empty `## Unreleased` above it. Then push the tag.
- Pushing a tag runs `.github/workflows/release.yml`, which extracts that section with `.github/scripts/changelog-section.sh` and creates the GitHub release (a pre-release when the tag contains `-`) or replaces an existing release's notes. **It fails if the changelog has no section for the tag**, so a tag cannot be released without one.

## Functional tests

- **Every functional test extends `Tests\Functional\FunctionalTestCase`**, which extends API Platform's `ApiTestCase` (`ApiPlatform\Test\ApiTestCase` on 5.x, aliased from `ApiPlatform\Symfony\Bundle\Test\ApiTestCase` on 4.4), so HTTP and console tests share one base class. One test method per behaviour, named `test_<behaviour in snake case>`; a `#[DataProvider]` names each row (`yield 'a tag with a comma' => [...]`).
- **Use the shared traits in `tests/Functional/Trait` before writing your own**, one per kind of helper, each with its own `<Trait>Test.php` that runs it on the test app. A helper only one area needs goes in `tests/Functional/<Area>/`; a method joins a shared trait when a second area needs it, with a test there. Every method is `protected static`. `ApiRequestTrait::requestJsonLd()` (content type per method), `JsonTrait` (dotted node paths such as `member[0].@id`, schema files in `tests/Functional/assets/schema`, validated by `justinrainbow/json-schema` 6, which enforces `const` and resolves `$ref` against `$id`: never give a schema or property an `$id`), `ResourceTrait` (`persistAndFlush()`, `iriOf()`, `findByIri()`), `AuthenticationTrait` (`loginAsAdmin()`, `loginAsSuperAdmin()` by JWT cookie, `loginAsUser()` by Bearer), `SiteTrait`, `PublishableTrait`, `CollectionTrait`, `UploadsTrait` (files in `tests/Functional/assets/files`), `ManifestTrait`, `CwaFixtureTrait::buildSite()` (any other site shape, through `CwaFixtureBuilder`).
- **Set-up helpers persist, flush and reboot the kernel**, so the request under test starts with a fresh container and the profile, log handler and HTTP client traces hold only what it did. Set-up written by hand calls `static::rebootKernel()` before the request, or a purge from the set-up flush shows up in its assertions. The entities a helper returns are detached: read ids and IRIs, and reload with `findByIri()` to see a change.
- **Assert purges and response tags with `CacheTagsTrait`**, which splits on `/[,\s]+/` (see the purger trap below); `traceOutsideAnHttpRequest()` returns the HTTP client collector for a write outside a request. **Mercure with `MercureTrait`**: `mercureUpdates()` reads the static `HubStub`, which keeps what set-up published (call `HubStub::clearPublished()` after set-up), and `mercureUpdatesInLastRequest()` reads the profiler. **Emails with `EmailTrait`** (`assertOneTemplatedEmailSentTo()`, `sentEmailLink()`, `setEmailLinkDefaultOrigin()`), **logs with `LogRecordsTrait`** (`assertLogged()`), cookies with `CookieTrait`, cache lifetimes with `CacheControlTrait`.
- **Console:** `ConsoleTrait::runConsoleCommand()` returns a `CommandTester` and dispatches no console events; `runApplication()` goes through `Application::run()`, so console listeners (the fixture load listener) run. Not `runCommand()`: Symfony 8.1's `KernelTestCase` defines a public one with another signature. After `runApplication()` the log handler and the HTTP client collector are empty, so assert a purge from a console run with `MockClientCallback::purgeRequests()`.
- **A route prefix** is `static::bootKernel(['routePrefix' => '/_api'])` before `createClient()`; `iriOf()` then returns prefixed IRIs. The real-time channel switched off is `static::bootKernel(['realtimeEnabled' => false])`, which, like the prefix, has its own cache directory and container class. The client's base URI is `http://example.com`, which the Mercure cookie's domain check and absolute URLs rely on.

## Testing and CI traps

- **The test app hashes passwords at bcrypt cost 4** (`security.yaml`). At the default cost 13 each hash took about 0.5 s, and every login and every user-token flow hashes.
- **Unit tests never boot a kernel; functional tests boot it only through `Tests\Functional\FunctionalTestCase`.** Both PHPUnit configs run `failOnRisky="true"`, and a Risky test fails Infection's initial run. `symfony/error-handler` before 7.4.17/8.1.5 leaks its exception handler on every boot (Risky); API Platform's `ApiTestCase`, which `FunctionalTestCase` extends, pops it, and a bare `KernelTestCase` doesn't. Wiring assertions (a tag, an argument) still belong on a bare `ContainerBuilder`: a booted kernel's autoconfiguration masks a missing tag.
- **Functional tests (`tests/Functional`, the `functional` testsuite)** run on the test app with `debug: false`, an in-memory SQLite database per process (`TEST_DATABASE_PATH=:memory:` in the PHPUnit configs, the schema created once) and a DAMA rollback around each test, so they are isolated per process for paratest's workers. Without that variable (the console) the test app uses its file database. The upload filesystems write under `public/uploads/phpunit-<pid>` (`TEST_UPLOADS_SUBDIRECTORY`, a runtime env in the test app's `services.php`), so parallel processes never list each other's files.
- **Anything a test writes must be per process**, because paratest runs the suites in concurrent workers that share the checkout and the temp directory. The test app's cache and log directories are `var/paratest-<TEST_TOKEN>/` under paratest (`AppKernel::processSuffix()`, from the worker's `TEST_TOKEN`) and `var/` otherwise, so each worker compiles and reads its own containers; the database is in memory and uploads are per pid (above). A test that writes a file outside those uses a name unique to the test (`tempnam()`, `tmpfile()`, or `sys_get_temp_dir()` plus `bin2hex(random_bytes())`) and removes it; never a fixed path under `sys_get_temp_dir()` or the repository. Paratest fails nothing for a collision: it shows up as an order-dependent failure, so reproduce it with `vendor/bin/paratest -p4` run several times, and with `API_PLATFORM_USE_SYMFONY_LISTENERS=1`.
- **`FunctionalTestCase` sets `$alwaysBootKernel = false`.** On API Platform 4.4 the default (`null`) makes `createClient()` boot a fresh default kernel, so a kernel booted with `routePrefix` or as the debug kernel was silently replaced; 5.x defaults to `false`. Boot any special kernel before `createClient()`.
- **The functional suite never rebuilds the container.** Warm the cache after a service, config or route change (`cache:clear -e test`, and delete `var/cache/test_*` for the prefixed and debug kernels; under paratest each worker's `var/paratest-<n>/`, warmed with `TEST_TOKEN=<n> tests/Functional/app/bin/console cache:clear` as CI does), and before a coverage run: compiled on a cold cache under coverage, compile-time code is attributed to tests that cannot kill its mutants.
- **The debug kernel** (`bootDebugKernel()`, tests in `tests/Functional/Debug`, `#[Group('debug')]`) is `debug: true` with `framework.profiler.collect: false`, in its own cache directory (`AppKernel`'s `profilerCollect` argument). It catches stopwatch and profiler bugs the `debug: false` app cannot: with collection off, a sub-request opened while the profiler service is still uninitialised has its stopwatch section left open (#501).
- **Never override a function in a namespace from a test** (a `namespace Silverback\ApiComponentsBundle\…;` block defining `bin2hex()`). PHP caches which function an unqualified call resolves to the first time it runs, so the override applies only if its file loads before the code under test first runs: always under `phpunit`, which loads every test file up front, and only sometimes under paratest, which loads a class when a worker reaches it.
- **Every sub-request goes through `Helper\SubRequest\SubRequestKernel`**, never `http_kernel->handle(..., SUB_REQUEST, false)` directly. Symfony's debug `TraceableEventDispatcher` opens a stopwatch section on `kernel.request` and closes it on `kernel.response`. It skips the close when the sub-request throws (no `kernel.response` with `catch: false`), and when the profiler, first instantiated during the sub-request, reports itself disabled (`framework.profiler.collect: false`, the usual test config). The caller's next `stop()` (API Platform's `api_platform.processor.write`) then fails with a 500 in dev and test only. `SubRequestKernel` starts a `cwa.sub_request` event in the caller's section and, after the sub-request, closes the sub-request's section only if that event is no longer visible, so a section that was closed properly is never popped twice. The `debug: false` app cannot catch this; `SubRequestKernelTest` pins it with a real `Stopwatch`, and `Debug\SubRequestStopwatchTest` on the debug kernel.
- **The test app runs the Varnish xkey purger (space-joined), production runs Souin (`', '`, chunked at 1500).** Never assert an exact purge or tag header; use `CacheTagsTrait::purgedCacheTags()` / `responseCacheTags()` and their assertions, which split on `/[,\s]+/`.
- **The test app imports routes with no prefix.** A test that needs `/_api` boots the kernel with `routePrefix`, which gets its own cache directory and container class.
- **Test doubles with static switches** (`HubStub`, `MockClientCallback`, `UnreachableDatabaseMiddleware`, `RejectedDeleteMiddleware`, `QueryCountingMiddleware`, `BeforeTransactionCallback`, `SwitchableMailer`, `KernelHttpClient`) are reset before and after every test by `FunctionalTestCase::resetTestDoubles()`, with the `EMAIL_LINK_DEFAULT_ORIGIN` and `ORPHANED_RESOURCES_NOTIFY_RECIPIENTS` env vars; a new switch goes there. Static because the kernel can reboot between requests. `QueryCountingMiddleware::count()` is how a functional test pins a query count; the profiler collects no Doctrine queries with `debug: false`. Logs are asserted through the `app.monolog.test_handler` Monolog `TestHandler`, because the harness runs with `debug: false` and the profiler's logger collects nothing.
- **Newly covering a large declarative file with a unit test costs MSI**, because its mutants start counting (functional coverage does not count). Answer with assertions on the wiring, not exclusions.
- **Every CI test step runs `vendor/bin/paratest`** over `phpunit/phpunit` from Composer, `--processes="$TEST_PROCESSES"` (4, a runner's vCPUs), after warming each worker's cache, **except the coverage leg, which runs `vendor/bin/phpunit` in one process** for Codecov. Keep `brianium/paratest` on a version that supports the installed PHPUnit major.
- **PHPStan baseline:** 65 findings, none of them `method.notFound` (#324 worked through all 23). Fixing a baselined finding means regenerating with `vendor/bin/phpstan analyse --memory-limit=1G --generate-baseline phpstan-baseline.neon`; a stale entry fails the job. Narrow with `instanceof` or a precise parameter type, never a `@var` override. `src/Resources/skeleton` is excluded.
- **Infection is not a Composer dependency**, so its dependencies never constrain ours. CI downloads the signed phar at `INFECTION_VERSION`; PHPUnit 13.3 needs 0.34.2+. `--only-covered` no longer exists.
- **Infection runs the `unit` testsuite only and collects its own coverage.** `testFrameworkExtraArgs: "--testsuite=unit"` in `infection.json5` applies to its initial (coverage) run and to every mutant run, and the CI steps pass no `--coverage`, because the coverage leg's report covers both suites for Codecov: a mutant covered only by functional tests would be run with none and counted as escaped, and the functional tests' class times would make mutants skip. The functional suite is too slow to mutate against: Infection times a covering test by its whole class's JUnit time, even with `--only-covering-test-cases`, and the kernel boot is covered by every functional class, so a third of the mutants exceeded the timeout and a run without skips took 48 minutes on 10 local threads. The coverage leg's `timeout-minutes` is 40 (the other `phpunit` legs keep 20): it runs both suites under coverage, then Infection's own unit coverage run, then the full mutation run on `main`; a job that hits its limit is reported as cancelled, not failed.
- **`timeout` is 30 s** (`infection.json5`). Infection skips, rather than runs, a mutant whose covering test classes' JUnit times add up to more than the timeout, and a skipped mutant is not counted. When the summary shows `Skipped`, find out which slow unit tests cover the line or raise the timeout; never accept a skip. Both CI Infection steps run `--only-covering-test-cases`, so a mutant runs only the test cases covering its line rather than every case of each covering class.
- **Infection's initial run is in random order** (`executionOrder="defects,random"`), with a process whose memory grows as the suite runs. A test that sets `memory_limit` sets it above the current usage (`Tests\Imagine\MemoryLimitAboveUsageTrait`), never to a fixed size: PHP refuses to lower the limit below the memory in use, so a fixed `256M` held only while the test happened to run early.
- **A covering test that passes with a PHP warning hides every other covering test from a mutant.** Infection runs each mutant's tests fastest first with `stopOnDefect` and `failOnWarning="false"`, so the first test that only warns (an undefined key under the mutation) stops the run with exit 0 and the mutant escapes, however many later tests would kill it. Assert a helper's whole output in each unit test that reaches it, not a count, and avoid `??`/casts whose mutation only warns.
- **Infection on a pull request mutates only the changed lines; every other run mutates everything.** The PR step fetches the base branch (unshallowing the checkout, so `git merge-base` resolves) and runs `--git-diff-lines --git-diff-base=origin/<base>`, with the same 80 gates (`minMsi` in `infection.json5`, `--min-covered-msi=80`), so each change must meet them on its own lines. A PR with no added lines in `src/` passes: Infection exits 0 with "Could not find any modified files", and `--ignore-msi-with-no-mutations` covers changed lines that produce no mutants (a reordered `use`), which would otherwise fail the gate at 0%. A mutant counts when its node overlaps a changed line, so a changed line inside an `if` also mutates the `if`.
- **The `phpunit` jobs (Symfony 7.4 and 8.1, lowest dependencies, NEXT) run both suites; the `functional` job runs the functional suite on each Symfony and API Platform combination, plus a `use_symfony_listeners` leg.** Coverage reaches Codecov only through the `phpunit` coverage leg, which also runs Infection.
- **The Codecov upload count is pinned in `codecov.yml`** (`codecov.notify.after_n_builds` and `comment.after_n_builds`, now 1: the `phpunit` coverage leg). Adding or removing a leg that runs `codecov/codecov-action` means updating both: too low and `codecov/project` fails on partial coverage before the last upload, too high and Codecov never reports. A branch without `/` also gets a `push` run (the `'*'` filter does not match `/`), whose uploads land on the same commit.
- **The Stryker badge comes only from `main`.** `logs.stryker.badge: "main"` in `infection.json5` sends the score only for a non-PR build of exactly `main`; Infection itself refuses a pull request build, and the PR step does not get `STRYKER_DASHBOARD_API_KEY`. Before this was configured nothing was sent at all and the badge was stale.

| Entity | Role |

### Page hierarchy and routes

- **Routes are the publication mechanism.** Page data is editable by IRI before it has a Route; a Route is created when it goes public. So hierarchy lives on `AbstractPage` (`$parentPage` / `$parentPageData`), never on `Route`: a parent must be settable before either page has a URL.
- **Parent = nested, always.** There is no `$nested` flag. Two FKs, because `AbstractPage` is a mapped superclass and cannot be an FK target. An `Assert\Expression` forbids setting both. `AbstractPage::validateNoCircularParent()` guards cycles on the API, but fixtures, `CwaFixtureBuilder` and SQL bypass it, so every hierarchy walk carries its own visited-id set.
- **An ancestor with no Route is skipped, never a boundary.** This applies to liveness (#224), reachability (#225), children listings and path cascades (#256). `getParentPageRoute()` returning null means "keep walking".
- **Route generation** (`RouteGenerator::create()`): slugify the title, prefix the parent route's path, suffix to resolve conflicts, set the route on the page. **It refuses (`UnroutedParentException`, 422 on `POST /_/routes/generate`) when a parent exists but has no route** (#245): the child would squat the parent's natural path. Explicit route creation is unaffected. **It validates the generated `path` and `name` itself** (`ValidationException`, 422) before touching the page or an existing route (#432): it runs after API Platform's validation, so nothing else checks what it builds, and SQLite never enforces `VARCHAR(255)`.
- **A page's and a page data's `title` defaults to `null`** (#439), and both columns are nullable: a title is never invented, so the module can tell an untitled page from a chosen title. **Route generation refuses an untitled page** (`ValidationException`, 422 on `title`) when the title is null or slugifies to nothing, checked after the unrouted-parent check and before anything touches the page or an existing route. `generatePath()` returns `null` for it, so a lookup by generated path never matches an empty path.
- **A redirect keeps its old path; only its name is suffixed** (#435). `createRedirect()` and `CwaFixtureBuilder::redirect()` add `-N` to a taken name through `Utility\RouteName::withSuffix()`, which shortens the base so the name fits 255 characters. Never append a suffix by concatenation: a name is an internal identifier, so shortening it changes no URL, whereas refusing would block a rename over a name the admin cannot see.
- **Path concatenation is recommended, not required.** Rendering depth comes from the manifest, not from the URL.
- `PATCH /_/routes/{id}` with `cascadeChildPaths: true` rewrites descendant paths and creates redirects. `GET /_/routes/{id}/children` is admin-only and unfiltered by publication. Both walk page-to-page, so a routed grandchild under an unrouted page is included. Both walks carry a visited set seeded with the starting page: the prefix check alone does not terminate a cascade to a path under the route's own path when an unrouted child loops back (#432). **The cascade is planned and every new descendant path validated before the inner processor writes anything** (#432); the write flushes the route first and each level after, so a failure part way through used to leave the tree half moved. A descendant violation is reported on `path` with the descendant's old and new path in the message.
- **A page's `uiComponent` has one stored form, the full component name `CwaPage<Name>`** (#425), as a layout's is `CwaLayout<Name>`. `Utility\PageUiComponent::fullName()` decides it; `PageUiComponentNormalizer` applies it to the request data before a `Page` is denormalized, so validation (and any `Length`) sees the stored, prefixed value. `CwaFixtureBuilder::page()` prepends the prefix itself, and `silverback:api-components:prefix-page-ui-components` (`PageUiComponentPrefixer`) upgrades rows stored short. Anything else that writes a page's `uiComponent` must store the full name.

### Route publication — `liveAt` (#224, #234)

`Route.liveAt` (admin-only): past = live, future = scheduled, `null` = draft with the URL reserved. The constructor and the column's `CURRENT_TIMESTAMP` default keep existing routes live; going draft is explicit.

- **Effective date = the latest `liveAt` in the chain** of routed ancestors, resolved at request time by `RouteLiveResolver` and memoised per request. A routed ancestor with `null` gates everything below it. Nothing is stored. Admins read it from `_metadata.effectiveLiveAt`.
- **Collections** filter on it through `RouteAncestorGateResolver`: one native recursive CTE returning gated route ids, applied as `NOT IN` so pagination and `totalItems` stay right (`PublishableExtension`'s shape). One self-reference with `LEFT JOIN` + `COALESCE` over both parent types, because PostgreSQL rejects two recursive branches. `UNION` (not `ALL`) terminates cycles. Table and column names come from `ClassMetadata`, so the table prefix is honoured. Verified identical on SQLite, MySQL 8, MariaDB 10.11 and PostgreSQL 16; MySQL 5.7 and MariaDB < 10.2 cannot run it.
- **The extension and the voter answer different questions, deliberately.** SQL answers which rows an anonymous caller may list; `RouteVoter` also applies `route_security`, which is per-token and cannot go into SQL.
- **A `route_security` `route` pattern is decided only by `Utility\RouteSecurityPattern`** (#537, #540), for both `RouteVoter` (`matches()`) and `RouteExtension` (`sqlCondition()`/`sqlParameter()`). It matches the whole path, `*` is its only wildcard, and every other character matches only itself, byte for byte: case-sensitive, accent-sensitive, no Unicode folding. `/user-area*` is a prefix, `*/user-area*` matches anywhere, `/user-area` is that path alone; `/User-Area/x` and `/üser-area/x` are not restricted by `/user-area*`.
- **The route list must never show less than the voter grants, nor the voter grant what the list hides** (#540). So the SQL compares bytes, never through the column's collation or `LOWER()`: MySQL and MariaDB `_ci` collations fold case and accents in `LIKE` (`/uber` matched `/über%`), and `LOWER()` is Unicode on PostgreSQL and MySQL (the Kelvin sign lowers to `k`) and ASCII-only on SQLite, so either made the list hide routes the voter served. PostgreSQL is `path COLLATE "C" LIKE … ESCAPE '!'`, MySQL and MariaDB `CAST(path AS BINARY) LIKE … ESCAPE '!'`, SQLite `path GLOB …` (its `LIKE` ignores ASCII case), and any other platform throws rather than compare in a collation. The extension runs that as one native query for the matching route ids and applies them as `NOT IN`, like `RouteAncestorGateResolver`, because DQL can express neither. `RouteExtensionTest` checks the list against the voter path by path; set `ROUTE_EXTENSION_DATABASE_URL` to run it on another database, as the `route-security-databases` CI job does for PostgreSQL 16, MySQL 8.0 and MariaDB 10.11. A new pattern feature must keep both sides in that test.
- **Public status for a gated route is 404.** `RouteVoter` still returns false; `UnpublishedRouteExceptionListener` rewrites 401/403 to 404 on the main request. The `NotFoundHttpException` **must not carry the original as `previous`**, or the firewall's `ExceptionListener` finds it and converts back to 401. A component reachable only through a gated route stays **401**, because `ComponentVoter` uses a sub-request the rewrite skips; `Route\RouteScheduleTest` pins that boundary.
- Redirects to a gated target still return the redirect, but `RouteNormalizer` does not reflect the target's page IRIs, and gated nodes are pruned from `redirectedFrom` for non-admins.
- **The cache cap uses a global `MIN(liveAt)`** (`RouteRepository::findNextLiveAt()`). Every effective transition is some route's own date, so it can only expire early. That it is global is the cascade guarantee: a go-live changes navigation on pages that never reference the route.
- **Never put `#[Silverback\Publishable]` on `Route`.** It is a draft/published pair and would add twin FKs and rewrite item queries. The shared scheduling predicate is `Utility\PublicationDate`.

### Route reachability (#225)

A Route reaches its own page **and every ancestor** through `parentPage`/`parentPageData`. `RouteReachabilityResolver` finds, for a routable with no route, any descendant route that passes `RouteVoter` (two-repository `findBy`, visited-id set, early exit, memoised). Used by `RoutableVoter` (which also checks page data using a `Page` as template) and `ComponentVoter::voteByRoute`.

- **Never `iterator_to_array()` a generator built with `yield from` without `false`** (#447): each inner collection's keys start at 0, so later items replace earlier ones. `ComponentVoter` lost a component's routed page that way when the component was also on an unrouted page.
- `ComponentVoter::voteByRoute` abstains (public) for a component in **no** page and denies for a component in pages none of which are reachable, falling through to `routable_security` so admins still see it. Denying both broke every test with unplaced components.
- Reachability is not denormalised. A column cannot express `route_security`, and an edge table was built and rejected (maintained state, rebuild command, upgrade step). A routeless page is absent from `GET /_/pages`.
- **`AbstractPage::$isReachableWithoutRoute` (#381) applies only to a page with no route**, and stands in for a live route at that node of the same walk, so a flagged page reaches its ancestors and its components, page data template and manifest follow with no voter change. A page with a route ignores it: its route decides (`liveAt`, draft included, and `route_security`). A flagged routeless page is still held back unless its **nearest routed ancestor** passes `RouteVoter`, exactly as for a routed child. Admin-only on read and write (`ApiProperty` security, like `Route.liveAt`); a flagged page stays out of `GET /_/pages`. The flag on a template does not reach its page data. `Route\ReachableWithoutRouteTest` is the authority.

### Manifest — `GET /_/resource_manifest/{id}`

`{id}` starting with `/` resolves a Route by path; a UUID resolves a `Page` or `AbstractPageData` (admin/draft). Owned by the `ResourceManifest` DTO so `RoutingPrefixResourceMetadataCollectionFactory` does not collide with entity routes. It is a performance requirement for admin as well as public rendering: it replaces 4+ serial round trips with one parallel batch.

- **Shape:** `resource_iris` is an array indexed by rendering depth (root first); each element is a tree `{ "iri": string, "children": [...] }` (#197). Depths split on `parentPage`/`parentPageData`. No per-node metadata; the front end derives types from IRIs (#198 closed).
- Built by `ResourceManifestNormalizer` with `ManifestDepthGroupTrait`. Blank nodes (`/.well-known/genid/`) and `/_/resource_metadatas` are excluded via `ManifestIriFilterTrait::shouldSkipIri()`, shared with `CwaTagCollector` so the body and the tag header cannot disagree.
- **A relation is embedded only when the related resource has a field in `Route:manifest:read`.** `Route.page/pageData`, `AbstractPageData.page`, `AbstractPage.route/parentPage/parentPageData`, `Page.componentGroups`, `Layout.componentGroups` (#306) and `AbstractComponent.componentGroups` (#309) carry it.
- **`Layout::getComponentGroups()` keeps `readableLink: false`** so `GET /layouts` returns bare IRIs (the module needs that). `LayoutManifestNormalizer` expands them only in the manifest context. **A layout is listed once, at the shallowest depth using it**, because the module maps IRI → depth and a deeper duplicate would get the wrong `path` header. Only layouts are deduplicated: a shared template `Page` appears per depth because its dynamic positions resolve per depth.
- **Every string value starting with `/` is taken as an IRI** by `ManifestDepthGroupTrait::buildDepthNodes()`, because bare-IRI relations (`readableLink: false`) arrive as strings. So a normalizer that adds a path-like field after the groups are applied must skip it under `CwaTagCollector::MANIFEST_CONTEXT_KEY`, as `RouteNormalizer` does for `redirectPath` (#444). `every IRI in the manifest should resolve` checks a manifest anonymously.
- **A redirecting route's manifest is the target's full manifest, by design**: `RouteNormalizer` copies the target's page and page data onto it, so the app can redirect internally without another round trip. Do not shrink it to the route alone.
- `pageDataProperty` positions resolve during manifest generation through the `cwa_current_page_data` context key set by `PageDataNormalizer`. Draft components are excluded for anonymous callers.
- The manifest body contains only IRIs; each follow-up fetch is voter-checked.
- **The component tree is loaded before the manifest is normalized, one query per owner level** (#542): `ResourceManifestNormalizer` calls `Helper\Page\ManifestTreeLoader::load()`, which collects the rendered pages (a route's redirect chain, page data templates, every `parentPage`/`parentPageData`) and their layouts, then fetch-joins `componentGroups` → `componentPositions` → `component` for the pages, the layouts and then each level of components, with a visited set and `IN` lists chunked at 500. Normalization then walks only initialised collections. **Doctrine loads an inverse one-to-one eagerly, one query per entity, whenever it hydrates the entity without fetch-joining it** (#552), so a publishable component's `draftResource` cannot be left to the generic fetch-join: before each owner level's query, one scalar query finds the publishable components in the owners' groups (`CASE … INSTANCE OF` over the discriminator map's classes `PublishableAttributeReader` configures, so association names are never hard-coded), then one query per publishable class present hydrates them with `c.<reverseAssociationName>` and the draft's own reverse association fetch-joined, which is what stops the lookups; the generic fetch-join then finds them in the identity map. The drafts found are owners of the next level, so a swapped-in draft's groups come in that level's query. So an owner level is two queries plus one per publishable class present when the application has any publishable component class, and one query when it has none. It loads nothing the normalizers would not, and decides nothing: every voter and normalizer still runs. `Page\ManifestTreeQueriesTest` pins a constant number of tree queries whatever the page's size, and `Page\ManifestPublishableTest` the same total for 3 or 12 publishable components, anonymous and admin.
- **A manifest builds no media objects** (#542): `UploadableNormalizer` skips `MediaObjectFactory` under `CwaTagCollector::MANIFEST_CONTEXT_KEY`, because none reach the body, so a manifest makes no storage call and no file info query. `Page\ManifestUploadableTest` pins both with `CountingFilesystemAdapter` (a test double decorating the `local` and `in_memory` adapters) and `QueryCountingMiddleware::queriesOnTable()`.
- **A manifest neither counts a publishable component's locations nor validates it for publishing** (#542): `PublishableNormalizer` skips `countLocations()` and the `PublishableValidator::PUBLISHED_KEY` validation under `CwaTagCollector::MANIFEST_CONTEXT_KEY`, because both only feed `_metadata`. Anything that changes an IRI still runs there: the draft/published association context, and `ComponentPositionNormalizer`'s draft swap and hidden-publication recording (the manifest's `Expires`). `Page\ManifestPublishableTest` pins the tree, the `Expires` and the queries.

### Caching

Resources are fetched and cached **individually**. Never embed related data outside the manifest; return IRIs. A write purges that resource's tags, not everything referencing it.

**Tag grammar, three shapes** (none contains a comma or space, so all are separator-safe):
1. A **resource IRI** (`/…`, or an absolute URL under `ABS_URL`).
2. A **singleton flag**: only `cwa-html`, the rendered-HTML tag. `HttpCachePurger::RENDERED_HTML_TAG` is a cross-repo contract with the module's `RENDERED_HTML_SURROGATE_KEY`; a mismatch fails silently.
3. A **grouping key** `<kind>:<resource-iri>`. The only one is `manifest:<entity-iri>`.

- **Manifest tags (#227):** `CwaTagCollector` is registered as `api_platform.http_cache.tag_collector` (the primary id AP references; bundle id and FQCN are aliases). Defining it replaces AP's default for every resource, so its default branch reproduces AP's behaviour exactly (keyed by IRI), minus blank nodes and resource metadata. For a manifest it emits only `manifest:<AbstractPage IRI>` per depth, detected by `CwaTagCollector::MANIFEST_CONTEXT_KEY` (not `$context['operation']`, which JSON-LD's normalizer unsets on the DTO → resource transition). Keyed by the page entity, not the Route, so path- and UUID-addressed manifests share it. **A component content edit purges no manifest**; membership changes do. `ManifestKeyResolver` walks upward from a written `Route`/`AbstractPage`/`Layout`/`ComponentGroup`/`ComponentPosition` (breadth-first, visited set, `WeakMap` memo); its type switch is the trigger list. A page data manifest also carries its template page's key, so one template write drops all of them. A content edit on a `pageDataProperty`-bound component still purges, because `PropagateUpdatesListener` gathers the owning page data.
- **Cache-safety headers (#200):** `CacheHeadersEventListener` marks authenticated responses for `http_cache.personalised_resource_classes` (default `Route`, `ResourceManifest`, `ComponentPosition`, plus any Publishable) as `private, no-store`. Anonymous responses stay `public`. The gate is an authenticated token, not a cookie. No `Vary: Cookie`.
- **Scheduled expiry (#227):** the same listener caps `s-maxage`/`max-age` at the next global `liveAt` for `http_cache.scheduled_expiry_resource_classes` (default `Route`, `RoutableInterface`, `ResourceManifest`), and at the response's `Expires` when sooner (RFC 9111 gives `s-maxage` precedence, so `Expires` alone is ignored by shared caches). It runs at `POST_RESPOND - 1` because `PublishableEventListener::onPostRespond()` writes `Expires` at `POST_RESPOND`. Publishable collections get no `Expires`. A scheduled go-live is not a write, so no tag can fire for it; expiry is the only mechanism.
- **A hidden component still decides the position's cache (#492).** Its IRI stays a response tag, because the relation is normalized before the key is dropped. A future `publishedAt` it was hidden for is recorded on the main request (`CacheHeadersEventListener::NEXT_PUBLICATION_ATTRIBUTE`, the earliest wins), and the listener sets `Expires` to it for an anonymous response, which caps `s-maxage`, for positions and manifests alike. A write that changes a publishable component's publication date (publish, schedule, draft merge) also collects every position holding it in `PropagateUpdatesListener`, so the positions are purged and published to Mercure and `ManifestKeyResolver` purges the manifests placing them; an anonymous visitor never stored the component's IRI. A content edit still purges no position or manifest.
- **Rendered HTML (#232):** a write to a class in `http_cache.purge_rendered_html_classes` (default `SiteConfigParameter`, matched with `is_a`) adds `cwa-html` once per flush. Listed classes must be association-free, because associated resources are also collected. A purge fires once per Doctrine flush; do not build a debounce.
- **Explicit purges:** `silverback:api-components:purge-rendered-html` / `POST /_/rendered_html/purge` send only `cwa-html` (#243), never touching collected state. `silverback:api-components:purge-http-cache` / `POST /_/http_cache/purge` flush the whole cache via Souin's `PURGE <invalidation-url>/flush` (#290). Only a `SouinPurger` can flush; otherwise the command exits 0 and the endpoint returns 501. **Build the flush URL as `rtrim(url, '/') . '/flush'`**, never relative. There is no API-only flush, because HTML is built from API data. Both endpoints are `ROLE_ADMIN`, `input: false`, `output: false`, 204, and need `read: true` (with `use_symfony_listeners: true`, `PlaceholderAction` otherwise has no `$data`). Console commands are the deploy path, run with `kubectl exec` in the API pod, since Souin's admin API is bound to localhost there. They accept any Content-Type, so they rely on the JWT cookie's `SameSite=Lax` against CSRF.
- **Selective purge (#390):** `purge-http-cache --tag/--path` sends only those tags through `HttpCachePurger::purgeTags()`, the purger writes use, and never flushes. `--path` resolves with `HttpCachePurger::getRouteTag()`, which asks the IRI converter for an unsaved `Route` at that path, so it is the tag a write to that route purges, import prefix included. Never rebuild that string by concatenation. It does not look the route up: a cached page can outlive its route. A tag with whitespace or a comma is refused (exit 2), because the purge header would split it. No purger: exit 0 and say so, like the flush. The endpoint is the same purge (#484).
- **Maintenance mode (#549):** `silverback:api-components:maintenance on|off|status` (`MaintenanceCommand`) is the deploy path for the `maintenanceModeEnabled` site config row. It writes through Doctrine, so `PropagateUpdatesListener` purges and publishes as for an API write (Mercure works from the console: `AnonymousResourceReader`'s sub-request needs no main request, and site config goes out privately only), and stores `'true'`/`'false'`, the string the module's settings page writes (`JSON.stringify` of the boolean). `Utility\MaintenanceMode` decides on/off as the module does: `null`, `''`, `'0'` and `'false'` are off, anything else on. Then, changed or not, it purges `cwa-html` plus `HttpCachePurger::getResourceTags()` of the row explicitly and fails loudly (exit 1), so the deploy knows the cache was dropped; no purger is exit 0 and says so; a DBAL exception is exit 1; an invalid state is exit 2 before anything is touched. **It must touch only the site config table**, because it runs before `doctrine:migrations:migrate` against the old schema: `PropagateUpdatesListener` therefore never looks up `Collection` components for a `SiteConfigParameter` write (configuration, never content, and its write already purges `cwa-html`). Anything new on that write path must not query another table; `SiteConfig\MaintenanceCommandTest` names the tables touched.
- **Scoped purge endpoint (#484):** `POST /_/http_cache/purge` flushes only when the request has **no body at all** (empty content). Any body is a scoped purge or a 422, never a flush: `{}`, `null`, `[]`, malformed JSON, an unknown key, an empty or non-list `paths`/`tags`, or a bad item are violations on `paths`/`tags`/`paths[i]`/`tags[i]` (the root for a body that is not an object or names neither key). `paths` and `tags` may both be sent; the union is purged once. `ScopedPurgeRequest` is the one parser and applies the command's rules: a path starts with `/` and resolves through `getRouteTag()` only (no expansion), a tag (given or resolved) with whitespace or a comma is refused. The operation keeps `input: false` and reads `$context['request']`'s content itself, because a deserialized body could not tell no body from `{}` nor make malformed JSON a 422. Scoped with no purger is 501, unlike the command's exit 0, because the endpoint's flush is 501 when unsupported.
- **Warm after a full flush (#484):** `http_cache.warm_after_flush` (off by default) makes `HttpCacheFlusher::flush()`, after every invalidation URL succeeded, call `HttpCacheWarmDispatcher`, which dispatches one `WarmHttpCacheMessage` per encoding (`gzip` for SSR, `br` for browsers and the CDN) on `messenger.default_bus`; `WarmHttpCacheHandler` runs `HttpCacheWarmer` over `PublicRoutePaths` (shortest first) with the configured `base_url`, `max_time` (per encoding), `concurrency`, `timeout` and `limit`. So the endpoint, `purge-http-cache` with no options and the fixture load flush all warm, and a scoped purge never does. **Never run the warm without a bus or in the flusher itself:** with no bus it logs a warning and warms nothing (unlike the orphan scan, which runs its handler inline), because a warm inside a php worker request holds the worker for up to `2 × max_time`. A site that enables it routes the message to an async transport; a synchronous route still runs it inline, which is the site's choice. A failed dispatch (Messenger's `ExceptionInterface` only) is logged at error and never fails the flush or the other encoding. It changes no response.
- **Cache warm (#442):** `silverback:api-components:warm-http-cache` (`HttpCache\Warm\HttpCacheWarmer`) requests through the cache what SSR requests: the route, then its manifest, then every manifest IRI, a redirect only its route. **A warm request is useful only under the exact key SSR uses, and a wrong key still returns 200**, so the headers are pinned request by request in `HttpCacheWarmerTest`. The key is the template's Souin `key` template plus the response's `Vary`: `Accept` (`/_api` only), the host (any dotless or `.local` host maps to `BROWSER_SERVER_NAME`), the normalised `Accept-Encoding` (Node 26's fetch sends `gzip, deflate`, so `gzip`), `path` (`Vary: path` on a page data position) and `preload`: Vulcain runs inside the cache and adds `Vary: Preload` whenever it answers with `Link` headers, which over SSR's plain HTTP is always. **`ModuleRequestHeaders` is a cross-repo contract** with the module's `cwa-fetch.ts` (`Accept`), `preload-headers.ts` and `manifestDepthPath()`/`createRequestHeaders()` (`path`: the route path at the IRI's deepest manifest depth, else that depth's page data IRI, else the route path); change both together. Routes come from `PublicRoutePaths`, which applies `RouteExtension` as an anonymous caller would see `GET /_/routes`, shortest first. Requests are anonymous. Follow-ups jump the queue of routes so each route is warmed whole before a `--max-time` stops it. After the command starts, nothing fails it: invalid options exit 2, and everything else exits 0. **A warm that cannot decode what it asks for never runs** (#488): `HttpCacheWarmer::canDecode()` is false when the `Accept-Encoding` lists `br` and `brotli_uncompress` is not callable (the function name is a constructor argument, so tests pass `base64_decode` or a missing name, never the machine's extension), and then the command refuses with exit 2 and `WarmHttpCacheHandler` logs at error and requests nothing; the check is in the handler, not the dispatcher, because the handler's process is the one that decodes. **A route or manifest body it cannot decode counts as failed, with the reason as the request's error**, so a skipped follow-up never reads as a normal request in the summary. **Spreading a warm across pods is `--requests-per-connection=N` (`warm_after_flush.requests_per_connection`), off by default** (#553): a Kubernetes Service balances per TCP connection and the client keeps connections alive, so every Nth request started carries `Connection: close`, the only header it may add (hop-by-hop, never part of a cache key), and 1 closes every connection. It is a request header, not a client reset or a curl option: `reset()` closes no connection on any Symfony client, it works on every HTTP/1.1 client, and curl closes the connection itself even when the server ignores it. Over HTTP/2 it does nothing, so it is for a plain-HTTP Service URL. `HttpCacheWarmerConnectionTest` counts real connections on curl against `tests/HttpCache/Warm/assets/keep-alive-server.php`, a keep-alive server the test starts (`php -S` closes every connection, so it cannot tell). `KernelHttpClient` sends a functional test's warm into its kernel.
- **Purge failures (#311):** after a write, a failed purge is logged at error and swallowed, and later propagators (Mercure) still run. `reset()` runs in a `finally`. An explicit purge fails loudly: exit 1, or 502. Catch only HttpClient's `ExceptionInterface` and AP's `RuntimeException` (tag too long), never `\Throwable`. `SurrogateKeysPurger` throws inside `purge()` itself, because the discarded response's destructor runs there.
- **Route write tags (#313):** `<route import prefix>/_/routes` plus `…/_/routes/<path>` (e.g. `/_api/_/routes//my-route`), and the old path's IRI on a path change. The tags are identical from HTTP and CLI. A sub-directory deployment needs `framework.router.default_uri` for CLI purges to match.
- Response tag headers are unbounded; the limit is the proxy's buffer (a 502 at the proxy, never truncation).

### Mercure

- `symfony/mercure` ^0.8 || ^0.9 and `symfony/mercure-bundle` ^0.5 || ^0.6 are runtime requirements (#270, #384); the lowest-dependency CI legs run 0.8/0.5. Keep the hub's `protocol_version` explicit: 0.5 defaults to the legacy protocol, 0.6 to 1.0, and **the bundle speaks only the Mercure 1.0 protocol** (#377): the hub needs `protocol_version: '1.0'` and `jwt.claims` `iss`/`sub`/`client_id`. A 0.x hub fails loudly when the cookie is built (the legacy factory rejects `urlpattern` grants). `PublishableAwareHub` mirrors `Debug\TraceableHub`: implements `RemoteHubInterface` and forwards every method including 0.8's `getProtocolVersion()`/`getCookieName()`.
- **A failed publish after commit is logged, not a 500** (#283). Per update, catch only Mercure's `RuntimeException` and HttpClient's `ExceptionInterface`. An invalid JWT (`InvalidArgumentException`) is configuration and still throws.
- Subscribe grants are URL Patterns (`match_type: urlpattern`) built from the operation's registered route path (so they include the import prefix), with the format suffix dropped and `{name}` turned into `:name` (#304, #377).
- **A URL Pattern with no query part matches any query string**, so `…/:id` would grant every `?draft=1` topic. Every grant ends in `\?` (no query) or `\?draft=1`; never emit one without. Checked against a real 1.0 hub.
- **One invalid pattern makes the hub reject the whole token** (401), and the Go implementation rejects a group name starting with `_` (`:_format`). Never emit a format group.
- The token's `aud` defaults to the hub's `public_url`, and the bundle publishes through the internal `url`, so the hub must pin `resource_identifier` to the public URL or every publish is 401.
- The cookie is `__Secure-mercure_access_token`. symfony/mercure throws when building it for a plain-HTTP `public_url`; a plain-HTTP setup sets a prefix-less `cookie_name` on the hub.
- **The subscriber cookie and its token share the refresh token's lifetime** (#498): `MercureAuthorization` passes `exp` = now + `refresh_token.ttl` as an additional claim, which symfony/mercure (0.8 and 0.9) uses for both the token and the cookie, so the browser drops the cookie exactly when the hub would refuse it. `mercure.default_cookie_lifetime` does not apply to it. Pass `exp` as a `DateTimeImmutable`: an int is read as a relative lifetime for the cookie and is not accepted by lcobucci for the token. Re-issued on login and every JWT refresh, so a session slides; a clear (`getClearAuthorizationCookie()`) expires it.
- **A clear expires the subscriber cookie, never re-issues it.** `MercureAuthorization::getClearAuthorizationCookie()` (logout, an invalid or expired JWT, a failed `/me`) is symfony/mercure's `createClearCookie()` with the bundle's SameSite, so it has the login cookie's name, path, domain and secure flag and reads nothing from the security context: `LogoutEvent` is dispatched before the firewall clears the token, so a cookie built from grants there carries the signed-out user's grants. Afterwards the browser holds no grants, like a visitor who never signed in. **A failed `/me` expires the Mercure cookie whenever the request carries it, with or without the JWT cookie**: the JWT cookie expires with the session, the Mercure cookie does not, so an expired session sends only the Mercure cookie. A failed `/me` carrying neither sets no cookie.
- **The public update is what an anonymous `GET` returns** (#494). `MercureResourcePublisher` gets it from `AnonymousResourceReader`: an internal `SUB_REQUEST` (`catch: false`) for the resource's IRI with the writer's cookies, `Authorization`, body and conditional headers stripped, and the token storage set to `null` for its duration and restored in a `finally`. The firewall never runs on a sub-request, so clearing the token is the only way to be anonymous there; never swap the token inside the writer's request itself. A 401/403/404 (or a security exception) means anonymous callers cannot read it. Anything else propagates.
- **A public delete `{"@id"}` goes out only when the write itself took the resource from public to not public**, because a delete reveals the IRI (a route's IRI is its path). `MercureResourcePublisher::leftPublicInThisWrite()` decides it from the written entity's UoW change set, captured at `onFlush` (the change set is gone by `postFlush`, so a re-add keeps the first answer): a publication date or a Route's `liveAt` moving from active to inactive (future or null), a page's or page data's `route` unset, or its `parentPage`/`parentPageData` changed (then only if the anonymous read is denied). An unreadable resource with none of these gets nothing on the public topic; the private update still goes out. Never decide it with a before-state read. Descendants a write hides without being written get no message: a known limitation.
- **Services that memoise caller-dependent answers on shared objects implement `Utility\CallerScopedStateInterface`** and are tagged `silverback.api_components.caller_scoped_state` (`RouteReachabilityResolver`, `ResourceMetadataProvider`): the reader isolates them for the sub-request and restores them after, because entities are shared with the writer through the identity map. A new memo keyed by an entity or `_metadata` whose answer depends on the token must join the tag. `RouteLiveResolver` memoises only dates, which are caller-independent.
- **The anonymous read must not write or touch the writer's response.** It carries `AnonymousResourceReader::REQUEST_ATTRIBUTE`: `PublishableReadStateProvider` skips the due-draft merge for it (a flush inside `postFlush`), and `ComponentPositionNormalizer` records no next publication on the writer's request. `JWTEventListener::onKernelResponse()` acts only on the main request, or a sub-request takes the refreshed JWT cookie. A denied sub-request leaves its stopwatch section open (`catch: false` skips `kernel.response`), so the reader closes it.
- **The writer's view goes privately to admins on `<iri>?draft=1`, after the public update**, and only when it differs from the public payload once the identifiers made per serialization (blank-node `/.well-known/genid/` and `media_objects` `@id`s) are ignored. A draft (inactive, or still holding its published resource) is never read anonymously: it goes only privately on `?draft=1`, preceded by a public delete of its plain IRI only when the write moved an active publication date to an inactive one. `PublishableAwareHub` leaves a bare `{"@id"}` on a topic without `?draft=1` public.
- **Every class's admins hold `<pattern>\?draft=1`**, not only publishable classes': `PublishableStatusChecker::isGranted()` falls back to the bundle's publishable permission for a class that is not publishable. The plain `\?` grant is held by every signed-in user, so it cannot carry admin data.
- **Both updates of one resource take one path, in order.** Through Messenger they are one `PublishMercureUpdatesMessage` handled by `PublishMercureUpdatesHandler`, which publishes them in order to one hub; a single update is still dispatched as an `Update`. An application routing `Update` to an async transport must route the message too. The module keeps the last message per `@id`, so a private update overtaken by the public one would strip an admin's view.
- **Each created or updated resource costs one sub-request** (deletes and drafts none). A reorder costs one per position whose `sortValue` changed; a publication-date change one per position holding the component; a page data edit one per dynamic position bound to the changed property.
- **`PublishableAwareHub` passes through any update whose data names no resource** (no string `@id`, such as a `CwaRealtimeEvent`): it reads `@id` only to decide a draft upgrade, and resolving a missing one was a TypeError.

### Real-time channel (#559)

`POST /_/realtime` (`Realtime\ApiResource\RealtimeEvent`, `RealtimeEventStateProcessor`) lets an admin's tab publish its own event through the hub. Presence is one use: the module's convention is `event: "presence"` with `data: {page, state, component?, componentPosition?, field?, device?}`, a heartbeat every 15 s, and no lock. The bundle keeps `data` opaque.

- **`realtime.enabled` (default `true`) is the kill switch, and it removes the resource rather than refusing it.** `RealtimeEvent` lives in its own mapping directory, `src/Realtime/ApiResource`, which `prependApiPlatformConfig()` registers only when enabled (the `enabled_components` precedent), so off is a 404 from the router for everyone, before the firewall. `MercureAuthorization`'s `$realtimeEnabled` then grants no realtime topic and never calls `getRealtimeTopic()` (which would throw for a missing operation). `lastWrite` does not depend on it. Never move `RealtimeEvent` back under `src/ApiResource`, which is always mapped. So `enabled` is decided when the container is compiled and must be a literal boolean: `prepend()` reads the raw config before env placeholders exist, and the node refuses a string (an `%env()%`) by name rather than with the bare type error. Functional tests boot `static::bootKernel(['realtimeEnabled' => false])`, its own cache directory and container class.
- **The body is read from `$context['request']`, never deserialized** (`input: false`, `read: true`, as the purge endpoints). `RealtimeEventRequest::fromRequest()` is the one parser, in this order: over 16384 bytes is 413; then the content type: JSON (`application/json`, `application/ld+json`) accepts any event, `text/plain` (what `navigator.sendBeacon` sends for a string) only `event: "presence"` with `data.state: "left"`, and anything else (another `text/plain` body, a form, multipart, no content type) is 415; then validation, 422. `text/plain`, a form and multipart are CORS simple requests, which is why only the leaving beacon may use one. The beacon check reads the decoded body with `array_column()` only, so it never reads a missing key. **Before all of that, a `text/plain` body with `Sec-Fetch-Site: cross-site` is a 403** (`RealtimeEventRequest::isText()`), before the body is read, the user resolved or the limits counted: a CORS simple request is the only kind a hostile page can send without a preflight, so a JWT cookie with `SameSite=None` would otherwise let any site publish a leaving beacon as the admin into every other admin's editor. **A cross-site JSON body is never refused here**: it needs a CORS preflight, which the application's CORS config (nelmio) decides, so a legitimate cross-site front end with a `SameSite=None` cookie keeps working. `same-site` text is accepted (a front end on a sibling subdomain), so a same-site origin, and a browser that sends no `Sec-Fetch-Site`, still rely on the cookie's `SameSite`.
- **Validation:** a body that is not a JSON object is a 422 at the root; otherwise only `clientId` (a UUID), `event` (`^[a-z][a-z0-9_.:-]{0,63}$`) and `iri` (string or null) are validated, each a violation on its field. `data` is kept as decoded with objects as `stdClass`, so `{}` is republished as `{}`, never `[]`. Unknown keys are ignored, so a `user` in the body never reaches the payload. `data` that `json_encode()` cannot write again (a literal such as `1e999`, which decodes to `INF`) is a 422 at `data`, before the limits are counted; an integer beyond `PHP_INT_MAX` is republished as the float a browser's `JSON.parse` gives it anyway.
- **The payload is `{"@type": "CwaRealtimeEvent", "v": 1, clientId, user: {id, name}, event, iri, data, sentAt, expiresAt}`**, one private `Update` with no SSE `type`, `id` or `retry`, so it reaches the module's `onmessage`. `v` (`VERSION`) changes only when the module must read the payload differently. `user` comes from the token through `RealtimeUserResolver`: an `AbstractUser`'s IRI and username (never the email), any other user's identifier for both. `expiresAt` is `sentAt` + 45 s (`LIFETIME_SECONDS`), from the `clock` service.
- **The publish is synchronous, never through Messenger, bounded at 1 s, and its failure is never the caller's**: a refused, unreachable or timed-out publish (`MercureRuntimeException`/HttpClient `ExceptionInterface`) is logged at error (#283) and the response is still 202, since presence is best effort and the next heartbeat repeats it. An `InvalidArgumentException` (JWT configuration) still propagates. **The 1 s bound applies to this publish only**: `RealtimeHubCompilerPass` (before optimisation, so the hub is not yet decorated) defines `silverback.api_components.realtime.hub` as a copy of the configured hub (`mercure.hub_name`, else `HubInterface`'s alias) whose HTTP client argument (index 4, the same in mercure-bundle 0.5 and 0.6, `Hub` or `HubFactory::create`) is that client wrapped by `RealtimePublishClient::bound()` (`withOptions(timeout: 1, max_duration: 1, max_retries: 0)`, retried without `max_retries` when the chain refuses it as an unknown option: a `RetryableHttpClient` anywhere in the chain, as `framework.http_client.retry_failed` makes the hub's client, otherwise retries a 502, 503 or 429 with delays and `Retry-After`, so only `max_retries: 0` keeps the whole publish near 1 s), so resource publishes keep the hub's own client and a hub's own `http_client` is bounded too. A hub the application defines itself (any other class or factory, such as the test app's `HubStub`) is aliased unchanged, so its client's bound is the application's config. The copy is not decorated: `PublishableAwareHub` would pass a realtime update through anyway, and the profiler's `TraceableHub` does not see it.
- **Topic and grant come from one method, `MercureAuthorization::getRealtimeTopic()`**: the absolute base from `RequestContext` plus the route path of the operation named `RealtimeEvent::OPERATION_NAME`, import prefix included (`http://example.com/_/realtime`, `https://<host>/_api/_/realtime` under the template). The subscriber cookie adds `<topic>\?` after every resource grant only when the channel is enabled and `isGranted(new Expression(RealtimeEvent::SECURITY))`, the operation's own security, so who may receive is exactly who may send; a non-admin's cookie grants nothing matching it. No token is a denial; any other error propagates. Never reuse `isOperationAccessible()` for it (it grants on any `\Throwable`), and never give `RealtimeEvent` a `mercure:` option, or the resource loop would grant the topic to every signed-in user.
- **Two token buckets, both must accept**: per user IRI and `clientId` (`CLIENT_RATE_LIMITER_CONFIG`, a burst of 20 refilled at 10 a second, key `clientRateLimiterKey()`), and per user IRI across all their clients (`USER_RATE_LIMITER_CONFIG`, 60 refilled at 30 a second). Both are consumed on every valid event; when either refuses it is a 429 whose `Retry-After` is the longer wait of those that refused, and the other bucket's token stays spent. The user bucket is what bounds a client choosing a fresh `clientId` per request (a fresh client bucket each time, one more pool item each), so **never drop it or key it by anything the client chooses**. The user is the token's, never the body's. The bundle defines its own two limiters (`silverback.api_components.realtime.client_rate_limiter`, `….user_rate_limiter`, no lock, one storage) so it never depends on framework's `rate_limiter` section. **Their pool, `RealtimeEventStateProcessor::RATE_LIMITER_POOL`, is prepended to `framework.cache.pools` (adapter `cache.app`), never `set()` in a service file**: extension containers merge in bundle order, so a bundle definition replaced the pool an application declared. With a per-pod `cache.app` the limits are per pod; a site that wants them exact sets that pool's `adapter` in `framework.cache.pools`, which replaces the bundle's. The pool persists across functional tests in a worker and DAMA does not roll it back; each test's admin is a new user, so new keys, and a test that needs a 429 drains a bucket with `reserve()` rather than racing the refill. **Symfony 8.2 rounds a refused `RateLimit`'s `retryAfter` up where 8.1 rounds it down**, so a test through a real limiter accepts either second (`[1, 2]`), and the exact arithmetic is pinned with stubbed limiters. **Framework 8.2 no longer normalises a pool's `adapter` into `adapters` in its configuration tree**, so a test reading the processed config accepts both keys.
- **The writer echo is `_metadata.lastWrite: {clientId, userId, at}`**, set by `PersistedNormalizer` from `LastWriteResolver` on every resource it normalizes. `at` is the server's time (`clock`, RFC 3339 with milliseconds) when the write first resolved it, kept as a request attribute (`AT_ATTRIBUTE`) so every resource of one write, and its response, carry the same `at`; it exists because `modifiedAt` cannot order the module's 250 ms-debounced drafts (a `datetime` column, serialized to the second, and components are not timestamped by default). It is answered only for the **current** request (never `getMainRequest()`, which during the anonymous read is still the write), only for an unsafe method (so no shared cache can store it), never for a request carrying `AnonymousResourceReader::REQUEST_ATTRIBUTE`, only for a signed-in user and a UUID `X-CWA-Client-Id`. `AnonymousResourceReader` also strips the header. So it reaches the writer's response and the private `?draft=1` update, never the public one, and any write carrying the header always sends the private update, because the writer's payload then differs from the public one. `Realtime\LastWriteTest` pins it for a `POST`, a `PATCH`, a reorder (each position whose `sortValue` changed) and a move (every resource it publishes); a `DELETE` still publishes only `{"@id"}`.

### Optimistic concurrency (#561)

`AbstractComponent` and `AbstractPageData` (`VersionedTrait`) carry Doctrine's `#[ORM\Version]` integer `resourceVersion`. Each row has its own version: a new draft starts at 1 like any insert, and clients order updates per `@id`. It is `_metadata.version` on every normalization (`PersistedNormalizer`), so both Mercure updates carry it; a signed-in caller's successful response also carries it as a strong `ETag: "<version>"` and is then `private, no-store` (`ResourceVersionResponseListener`), because page data and non-publishable components are otherwise publicly cacheable. Anonymous responses keep API Platform's content-hash ETag.

- **Never hand-roll versions.** Doctrine writes the column (skipped on insert, so the column default 1 applies; `version = version + 1 WHERE version = <loaded>` on update, also when only a JOINED subclass table changed) and throws `OptimisticLockException` when the row moved since it was loaded, **with or without `If-Match`**: a write that loses a race at commit is a 412, never a silent overwrite. A delete is not version-checked by Doctrine, so only the early check protects it.
- **`If-Match` is compared with the row the URL addressed** (`ResourceVersionStateProvider`, outermost on `state_provider.read`, -60, so only a caller every access check let through learns the version; `PATCH`/`PUT`/`DELETE`; strong comparison: `"<n>"`, a list, or `*`). When the read returned another row than the URL's id (an admin's write to a published IRI redirected to its existing draft), any `If-Match` is a 412 with the draft: a live row and a draft can share a number. Without `If-Match` the redirect is unchanged. A PATCH to the draft's own IRI is checked against the draft.
- **Every 412 has the current resource as its body.** `ResourceVersionConflictException` is thrown by the provider, and by `ResourceVersionConflictStateProcessor` (outermost on `state_processor.locator`, 5) for an `OptimisticLockException` and for a `UniqueConstraintViolationException` while inserting a draft of a published resource (two first edits both create a draft; the draft join column is unique). `ResourceVersionResponseListener::onKernelException()` clears every entity manager and resets a closed one (a failed flush closes it), then answers with an internal `GET` of the caller's path and query (`SubRequestKernel`), status 412, `private, no-store`.
- **The order PATCH and `/move` ignore `If-Match`**; the rows they write still get a new version.
- **CORS is the application's**: a cross-origin front end needs nelmio to expose `ETag` and allow `If-Match`.
- `generate-fixtures` never writes the version (`EntityStateReader::managedFields()`). A race is reproduced with the `BeforeTransactionCallback` test double, which writes before the flush's transaction (a write inside it is rolled back with the refused flush).

### Collaboration state (#563)

`CollaborationState` stores a base64 Yjs update (`state`, up to `STATE_MAX_LENGTH` = 8 MiB of characters, a `TEXT` column whose length makes MySQL use `MEDIUMTEXT`) beside one field of a component or page data, so a tab that joins late loads it from the API rather than over the realtime channel. `htmlHash` is stored and never checked: the client uses a state only when the hash matches the HTML it loaded, which covers every write, import, discard and publish with no lifecycle hook in the bundle.

- **It belongs to exactly one of `component` or `pageData`**, two nullable many-to-one foreign keys like `AbstractPage`'s parents (`Assert\Expression`, 422), each `ON DELETE CASCADE`, so deleting a component or page data by any path (API, orphan delete, publish replacing a draft, SQL) deletes its states with no listener. Unique on (`component`, `field`) and (`pageData`, `field`), both in the database and as `UniqueEntity` (422).
- **A draft of a published component is stored as its published component** by `DraftComponentReferenceListener`, which re-points every single-join-column association to a component; nothing in `CollaborationState` does it. Validation runs before that flush, so the component uniqueness check goes through `CollaborationStateRepository::findByPublishedComponent()`, which looks the published component up first; without it a draft's duplicate reached the unique index as a 500. A never-published draft keeps its row when first published, so its state needs no move.
- **Filters are AP's `IriFilter`**, which converts the IRI with `fetch_data: false`, so the published IRI finds the published component's state even while an admin's item read of that IRI would resolve to its draft.
- **Versioned with `VersionedTrait`**, so `If-Match`, the 412 with the current state, the `ETag` and `_metadata.version` come from the #561 services unchanged.
- **`PropagateUpdatesListener` skips it entirely.** Its insert or delete otherwise collected every association, so each save republished and purged the component (a Mercure sub-request per save). It has no `mercure:` option and every response is `private, no-store`, so there is nothing to propagate.
- `generate-fixtures`, the orphaned resource scan and component usage never read it: a state is not content and does not make a component used.

### Security and users

- **A `PUT` on a user merges, never replaces** (#426). API Platform's `standard_put` defaults to `true` on 4.x and 5.x: the body is denormalized into a new object and every property is copied onto the stored one, including those nobody can write (password hash, tokens), so they took the constructor's defaults. `UserResourceMetadataCollectionFactory` sets `standard_put: false` on every `Put` of an `AbstractUser`, over any application default. `User\UserPutTest` pins it.
- **User email links** (#316): `RefererUrlResolver` uses `Origin`, else `Referer`, reduced to `scheme://host[:port]`, only if it matches `user.email_links.allowed_origins` (anchored by the bundle as `{\A(?:p)\z}i`), else `default_origin`, else the link is refused. The request host is not implicitly trusted. Request input may only be a `RelativeUrlPath`. **Never build an outbound link from a request header without an allow-list.**
- **A refused email link depends on which kind of email it is** (#326). Where the email is the job (password reset, both resends), the request is a 400 that changes nothing: build and send the email before flushing the token it carries. After a completed write (every email from `UserWriteNotifier::notify()`), the write keeps its status and `UserMailer::afterWrite()` logs the refusal at error; the verify and change-email emails serve both kinds, so the notifier must call their `…AfterWrite` variants. Only `UnparseableRequestHeaderException` is caught.
- **A throttled email request is a 429 with `Retry-After`** (#331), never a 200 that sends nothing. `UserDataProcessor` throws `RequestLimitReachedException` carrying the seconds remaining; the action returns it with nothing sent or changed. Each flow has its own `repeat_ttl_seconds`: `password_reset` (86400), `new_email_confirmation` (300) and `email_verification` (300). Never share one throttle between flows.
- **A failed send returns false whether or not a logger is wired** (#340): the logger is optional in `UserMailer`'s service locator, so check `has('logger')`; `get()` on a missing id throws.
- **The `…RequestedAt` timestamp starts the throttle, so `UserMailer` sets it only after `send()` succeeds**, and flushes it with the token then. A failed send (503) saves nothing: the action refreshes the user, so the token is not replaced by one nobody received.
- Actions calling `UserDataProcessor::findUserByUsername()` must catch its `InvalidArgumentException` and return 404; it throws rather than returning null.
- **Code typed against `UserRepositoryInterface` may call only what it declares** (#266, #336). The `@method` tags are not a contract, and PHPStan trusts them, so it will not catch a call to `find()` or `findOneBy()`. `loadUserByIdentifier()` matches username *or* email, so check the returned username and treat `NonUniqueResultException` as not found; `Repository\User\FindUserByUsernameTrait` does both. Test against `tests/Command/InMemoryUserRepository.php`, which implements only the interface.
- `user:create` throws `ValidationFailedException` rather than writing an invalid or duplicate user (#254). There is no DB unique constraint on username or email.
- Security routes: one path each. A duplicate path fails nothing and one route silently never runs; check with `debug:router`.
- `GET /_/health` (#312) is a plain Symfony route (not an AP operation, which would add JSON-LD, cache headers and tags), `no-store`, 200 or 503 with the DBAL message logged at warning and never returned. It is imported by `routing/all.php`.
- **Liveness is `/_/health/live`, readiness is `/_/health`** (#374). Liveness must fail only for what a restart fixes, so `LivenessAction` takes no dependencies and nothing on its request path may touch the database, a cache pool or a remote service; a database outage would otherwise restart every pod into a crash loop. `tests/Functional/Health/HealthTest.php` pins it with the unreachable-database double, which fails on `connect()` as well as on queries.

### Forms

- `/submit` has PATCH and POST only. **POST is a full submit** (`clearMissing = true`) and can succeed (#276). **PATCH is partial and validate-only**, never firing `FormSuccessEvent` (#251), because the module's live validation PATCHes every field.

### Uploads

- Stored as `<slug>-<token>.<ext>` with a `fileExists()` regeneration loop (#194); data-URI uploads keep a UUID name.
- **A data-URI upload is an `UploadedDataUriFile` built in test mode** (#457), so `isValid()` and `move()` never ask `is_uploaded_file()`. Out of test mode, every `File` or `Image` constraint refused it as "The file could not be uploaded.". A new kind of upload that is not a real HTTP upload needs the same, and a functional test through a constrained field (`DummyUploadableWithConstraints`).
- **A stored file's extension comes from its content type** (#402), through `Utility\StoredFileExtension`, the one place that decides it. The client's extension is kept only when it is one of the type's extensions (`.jpeg` stays), or when the type is `text/plain` or `application/octet-stream`, which say nothing about the format (`.md`, `.csv`). The slug still comes from the client name, or from the file's basename when only that has an extension: a client may send the form field key (`file`) as the client name.
- **An imagine variant of a filter set with `format:` (or an AVIF/HEIC source, #410) gets that format's extension** (`photo-1a2b3c4d.png` → `cache/<filter>/photo-1a2b3c4d.webp`). `FlysystemCacheResolver::getFileUrl()` applies it, so store, `isStored`, resolve and remove agree; `ImagineCompilerPass` gives every tagged `FlysystemCacheResolver` the `liip_imagine.filter.configuration` unless the application set the argument. Replacing, not appending, is safe because stored names are unique. Use `format: webp`, never liip's `webp.generate`: the bundle never resolves the `.webp` twin, so every filter would be generated twice.
- **Every stored-file write carries a `Cache-Control`** (#414): `uploadable.cache_control.original` (default `public, max-age=31536000, immutable`) on uploads, data-URI uploads included, and `.imagine` (default `public, max-age=2592000`) on variants. `null` writes none. `#[UploadableField(cacheControl:, imagineCacheControl:)]` overrides either: `null` (unset) inherits, `false` writes none. The immutable default is safe only because a stored name is never reused; keep it that way, or shorten the default.
- **The adapter's form is decided once, in `Utility\StoredFileWriteConfig`**: GCS reads `metadata.cacheControl` (built into the whole `metadata` array, since `Config::extend()` merges shallowly and would drop `contentType`), the AWS SDK and AsyncAws S3 adapters read `CacheControl`, anything else gets nothing. The classes are named as strings, because none of those packages is installed; `tests/Flysystem/cloud_adapter_stubs.php` declares recording stand-ins for the tests. Verify option keys against the adapter source on GitHub before adding one.
- **The adapter is found from the `Filesystem`**, through `FilesystemFactory::getAdapterOf()`, a `WeakMap` of the filesystems it created. So only an `api_components.filesystem.<alias>` service gets a `Cache-Control`; a `FlysystemCacheResolver` over a `Filesystem` the application built itself writes none.
- **A variant's field reaches `FlysystemCacheResolver::store()` by its source path.** `MediaObjectFactory` and `UploadableFileManager::storeFilesMetadata()` call `UploadableCacheControl::registerVariantSource($path, $field)` before generating, and the resolver reads `forVariantOf($path)`, which falls back to the bundle value (as for liip's own filter route). Anything new that generates variants must register first. The map is cleared on `kernel.reset`. `ImagineCompilerPass` injects `$cacheControl` into every tagged `FlysystemCacheResolver` unless the application set it.
- **A copy passes no `Cache-Control`; the stores keep the source's.** GCS copies metadata when the request sets none, the AWS SDK adapter copies with `MetadataDirective: COPY`, and AsyncAws's `copy()` ignores its config entirely. A clone of a file stored before #414 therefore has none until backfilled.
- **`#[UploadedImage]` (#455) is `Assert\Image` for an upload field**, a subclass, so every `Image` option still applies and the orphaned file report's `StoredFileConstraintValidatorFactory` (routing on `instanceof File`) reaches it. Its validator extends `ImageValidator`. Both validators resolve it through `UploadedImage::forFile()`, the one place that decides it: an SVG has every dimension, pixel, ratio, shape and `detectCorrupted` option dropped (only the file checks run), a raster image takes `maxPixels` from `uploadable.image_max_pixels` when the constraint sets none, and `{{ max_width }}`/`{{ max_height }}` (a 3:2 approximation) are written into the message text before validating. `allowSvg: false` refuses an SVG before any other check. The configured limit reaches the upload validator service and `StoredFileConstraintChecker`'s `$defaultMaxPixels`; the scan builds its own validators, so anything else that resolves the constraint must be given it too. There is no `allowNull: false`: `file` is null on every write that does not upload, and `requiredOnPublish` is how a file is required.
- Each `UploadableField` needs a **distinct `property:`**; `UploadableAttributeReader` throws when two share one (#199). Imagine runs only on raster images.
- `requiredOnPublish` adds a class-level `RequiresUploadedFile` in the groups publishing validates: `{ShortName}:published`, or the class's custom `#[Publishable(validationGroups:)]`, which replace it (#193, #252). **Those groups are decided only by `PublishableAttributeReader::getPublishedValidationGroups()`**, which `PublishableValidator` and the orphaned files scan both call.
- `urlGenerator: 'public'` asks the Filesystem (honouring the tag's `public_url` config) and falls back to `api` only on `UnableToGeneratePublicUrl` (#257).
- **A failed imagine filter never fails the request** (#410). `ImagineFilterGenerator::filteredImageUrl()`, the one entry point for reads and uploads, returns null for any `\Exception` from liip, Imagine or the driver: a missing source image (`NotLoadableException`, #299) is logged at warning, anything else at error, and the original is served. A PHP `\Error` still propagates: it is a bug. A functional reproduction of the missing source must warm the `_acb_file_info` cache first.
- **The output format of a variant is decided once, in `Imagine\ImagineOutputFormat`** (#410): the filter set's `format`, else `webp` for an AVIF, HEIC or HEIF source, else the source's own format. Vips cannot encode those (rokka/imagine-vips gives `heifsave` no quality, and Debian's libheif has no AV1 encoder), GD and Imagick often cannot, and liip cannot be configured around it per source. Two places must agree and both call it: the bundle's `FilterManager` (set on `liip_imagine.filter.manager` by `ImagineCompilerPass` unless the application set its own class) chooses the content from the binary's MIME type, and `FlysystemCacheResolver` chooses the stored name from the source path's extension, which since #402 comes from the content.
- **A stored variant with no file info row is read, not reported as `-1`** (#402). `MediaObjectFactory::createFromImagine()` reads it through `ImagineFilterGenerator::readStoredFilteredImage()` → `CacheManager::readStored()`, which only a `FlysystemCacheResolver` can answer (liip's `ResolverInterface` has no read), and saves the row. `-1` and an empty `mimeType` remain only for another resolver, or a variant that is missing or not an image. A variant is always generated before this point; `-1` never meant "not generated yet". The test app cannot reproduce it: its imagine cache is in memory and the kernel reboots between requests, so every request regenerates the variant and writes the row.
- **Every imagine filter is generated through `ImagineFilterGenerator`** (#387, #395), on read (`MediaObjectFactory`) and on write (`UploadableFileManager::storeFilesMetadata()`); never call liip's `FilterService` directly. A stored filter is only resolved, through `CacheManager::resolve()`, and an unstored one is generated with `FilterService::warmUpCache($path, $filter, null, true)` and then resolved, so each variant costs one `isStored()` storage check (#542). Never use `getUrlOfFilteredImage()`: it checks `isStored()` again, a second storage round trip per variant. For an unstored one, the cost is estimated as pixels × the measured rate for `liip_imagine.driver_service` (GD 12, Imagick 14, vips 8, anything else 14 MB per megapixel, from a thumbnail on bundled-GD PHP 8.4/8.5); if real usage plus the estimate exceeds the budget, the filter is skipped with a warning and the module falls back to the original. Otherwise `memory_limit` is raised to the budget for the generation and restored in a `finally`.
- **`silverback:api-components:imagine:generate` generates every variant not stored yet, so a request only resolves variants** (#413). It is the deploy path after adding a filter: a one-off Job, then purge the HTTP cache. `Helper\Uploadable\ImagineVariantGenerator` walks every concrete uploadable class, drafts included, in batches with `clear()` between them, never holding a table; a row's filters are the field's `imagineFilters` plus `getImagineFilters($property, null)`. Non-raster originals are left out, as on upload. It calls `UploadableCacheControl::registerVariantSource()` before generating a source's variants, as `MediaObjectFactory` and `storeFilesMetadata()` do, or the variants get the global `imagine` cache control instead of the field's `imagineCacheControl`. An unknown `--class` or a `--filter` missing from `liip_imagine.filter.configuration` exits 2 before anything runs. It asks `ImagineFilterGenerator::isStored()` before anything else, so a re-run reads no original and generates nothing. The variant's file info row comes from `CacheManager::store()`'s `ImagineStoreEvent`, so the helper writes none. Exit 1 only for a failed variant; an over-budget skip or a missing original is counted and exits 0. Registered in the extension, only when imagine is enabled. **It stops cleanly, never by being killed** (#418): `--limit` and `--max-memory` are checked by a `proceed` closure the helper calls before each variant it would generate, so a stop means a variant really is still missing, and the command exits `ImagineGenerateCommand::INCOMPLETE` (3) for the caller to loop in fresh processes; stored variants never count, and each run attempts at least one so a loop always progresses. `--max-memory` reads `Utility\ResidentMemory` (`VmRSS` from `/proc/self/status`, else `memory_get_usage(true)`), because libvips allocates outside `memory_limit`; never budget vips against PHP's own usage. The libvips operation cache (`Jcupitt\Vips\Config::cacheSetMax(0)`, only if the class exists, since the bundle does not require php-vips) is switched off for a non-dry run. A single original too large for the pod still kills the process: that is the Job's memory limit, not the bundle's. In a functional test, run it with `runConsoleCommand()` on the test's kernel: the test app's imagine cache is in memory, so a second run on a fresh kernel finds nothing stored.
- **`ImagineFilterGenerator::filter()` returns an `ImagineFilterResult`, whose outcome (`Resolved`, `Skipped` over the budget, `Failed`) is the only way to tell a skip from a failure**; `filteredImageUrl()` is its URL, null for both. A missing source (`NotLoadableException`) is `Failed`, though logged at warning.
- **The budget is `max(memory_limit, imagine.memory_limit)`** (default `320M`; `null` means no raise). An unlimited `memory_limit` (`-1`) is never checked or changed. Budget against `memory_get_usage(true)`: PHP enforces the limit on real usage and refuses (with a warning) to lower it below that, so a failed restore is logged, not hidden.
- **Measure GD memory only on a PHP with bundled GD** (the official Docker images). A system libgd, as on macOS, allocates outside the Zend memory manager, so `memory_get_usage()` shows nothing and an oversized image does not fatal locally. Imagick and vips allocate outside `memory_limit` everywhere; their rates protect the pod, not PHP.
- **Deleted-file markers are keyed per resource** in a `WeakMap` on `UploadableFileManager`, and transferred draft → published on merge. A property-name key leaked across requests in worker mode and deleted unrelated files.
- **Never delete a stored file before its replacement is in place, and never delete a path the resource still references.** `PublishableDraftMerger` snapshots paths, copies, then calls `deleteOrphanedFiles()`. `copyFilepath()` keeps the prefix and returns the original path when the source is missing.
- **A removed entity's stored file is deleted by `UploadableFileDeletionListener`, a Doctrine listener, never by an API listener** (#370). `onFlush` reads the paths of every scheduled deletion (initialising lazy references first, since `getFieldValue()` does not), per entity manager in a `WeakMap`; `postFlush` deletes each one, with its imagine variants and `_acb_file_info` rows, only when no row of that class still holds the path (a draft and its published version can share one; a publish removes the draft whose path the published row takes). A failed flush never reaches `postFlush`, so the file stays. A failed file delete is logged at error, catching only Flysystem's `FilesystemException`. This covers API deletes, every cascade, the orphan deleter and direct removal alike.
- **Removing imagine variants deletes their rows the way the resolver deletes their files** (#403, #405). `CacheManager::remove()` normalises its arguments as liip does (a string is one item, empty strings are dropped) before dispatching `ImagineRemoveEvent`, so `$paths` is always an array. In `FileInfoRepository::deleteByPathsAndFilters()`: no paths means every path; `null` filters means every **variant** row (`filter <> ''`), never an original's, because a resolver only ever removes variants; an empty filter list deletes nothing. An original's row is deleted only by naming the `null` filter, as `deleteStoredFile()` does. `CacheManagerRemoveTest` runs this through the real `CacheManager`, resolver and listener.
- **`FileInfoCacheManager::deleteCaches()` deletes rows with a DQL `DELETE`, not `remove()`**, because it runs in `postFlush`, where a scheduled removal would wait for an unrelated later flush. Never flush inside `postFlush`: the unit of work has not cleared its collection updates yet.
- **A normalizer never writes to the object it normalizes** (#389). `UploadableNormalizer` drops the file field and its storage property from its own output; nulling them on the managed entity let any later flush in the same request save `NULL` filenames for every uploadable already serialized.
- **A stored file's file info is read in one query per path** (#542): `MediaObjectFactory` calls `FileInfoCacheManager::resolveCaches()` (`FileInfoRepository::findByPathKeyedByFilter()`), the original under `''` and each variant under its filter, and passes the rows down. A variant missing from it, or generated in the same call (`ImagineFilterResult::$generated`), is looked up on its own (`resolveCache()`), because its generation wrote or replaced its row (#421) after the batch was read. The rows are held for one `createMediaObjects()` call, not memoised across the request, so there is nothing to reset. `Uploads\FileInfoQueriesTest` pins one query for an image with two stored variants.
- **Nothing on a read path flushes the shared entity manager.** `FileInfoCacheManager::saveCache()`, reached from `MediaObjectFactory::create()` and `ImagineEventListener::onStore()` during serialization, inserts its own row through DBAL (names from `ClassMetadata`) and skips a row that already exists. **A store event replaces the row** (#421): `ImagineEventListener::onStore()` deletes the `(path, filter)` row before `saveCache()`, because the row is keyed by the source path and filter, not the variant's name, so a changed filter writes a new file under an existing key. The resolver writes the file before the event fires, so a read between the delete and the insert rebuilds the row from the new file. The read paths stay insert-only.
- **An original's file info is stored with `filter = ''`, never `NULL`** (#392), so `unique_cache_item` on `(path, filter)` holds on every database (NULLs are distinct in a unique index). `FileInfo::$filter` stays `?string` (`null` for an original) as a hook over the mapped `$storedFilter`; DQL and `findBy` criteria name `storedFilter` and compare with `''`. Declare constraints and indexes as class-level `#[ORM\UniqueConstraint]`/`#[ORM\Index]`: ORM 3's attribute driver ignores `uniqueConstraints:`/`indexes:` on `#[ORM\Table]`. `saveCache()` keeps the row a concurrent request inserted first.
- `CwaFixtureBuilder` persists a `File` set on an uploadable fixture via `persistFiles()`, gated on `isConfigured()` (#195).

### Components

- `#[Silverback\ExplicitAllowOnly]` (#196): the type may only be placed in a group whose `allowedComponents` lists its collection IRI, enforced on both direct and dynamic positions. Exposed as `explicitAllowOnly: true` on the Hydra `supportedClass` (a locked contract; absent means false).
- `allowedComponents` matches by class-level (collection) IRI.
- **`ComponentGroup.maxComponents` (#464): `null` is unlimited, otherwise `Assert\Positive`.** It has exactly `allowedComponents`' serialization groups. What counts is `Helper\ComponentPosition\ListedComponentPositions::of()`, the positions the group's response lists (`ComponentGroupNormalizer` uses it too): every position, a dynamic `pageDataProperty` slot as one, minus a static position whose component `allowedComponents` hides. So the module's `componentPositions.length` is the count. A draft is reached through its published component's position, so the pair counts once.
- **The limit refuses adding, never holding.** `ComponentPositionValidator` checks it only for a position not already in its group's `componentPositions` (created, or moved in from another group), with a violation on `componentGroup`. A position already in the group can be re-sorted or re-pointed even when the group is over its limit, and lowering the limit deletes nothing. The over-limit state is not reported by the API; the module compares the two fields.
- **A component is never placed inside its own subtree** (#502). `Helper\ComponentPosition\ComponentCycleDetector` is the one rule: walk upward from a group (its owners, the groups holding them, their owners…, pages and layouts ending it) with a visited set, on the in-memory collections the write is building, and a published component and its draft count as one. `ComponentPositionValidator` refuses a placement on `component` only when the position is new or its `component` or `componentGroup` changed (the unit of work's original data), so editing inside a cycle already held is never blocked; `#[AcyclicComponentGroupOwners]` on `ComponentGroup::$components` refuses an owner from inside the group on `components`, only for an owner not already held (the owner's `componentGroups` snapshot). Unlike the limit, a cycle is never allowed to be added, but one already in the database (fixtures and SQL bypass validation) must still read: every upward walk (`ComponentVoter::getComponentPages()`, `ManifestKeyResolver`) carries its own visited set. `Component\ComponentPositionCycleTest` pins both.
- **A position written inside a component (`componentPositions` on a component write, the module's add flow) is validated by `#[AddedComponentPositions]`** on `AbstractComponent::$componentPositions`, which runs the whole `ComponentPosition` constraint on each position not already in its group, at `componentPositions[i]`. Never replace it with `Assert\Valid`: that would re-check every existing position on any component edit, so a group whose `allowedComponents` or limit changed later would block editing its components.
- **The client sends an order; the server chooses every `sortValue`** (#475). `sortValue` is read-only on the API (a `sortValue` in a body is ignored, and a 422 only beside an anchor); fixtures and server code still set it. An insert or a move takes `after`/`before` (write-only, unmapped position IRIs) on `POST /_/component_positions`, on a position embedded in a component write, and on a PATCH (of `componentGroup`, or within the group); with neither it goes at the end. An anchor that does not resolve to a position of the group (another group, deleted, unknown, not a position, itself) is a 422 on `after`/`before`, never ignored, and both anchors is a 422 on `before`. `PATCH /_/component_groups/{id}/order` (`application/merge-patch+json`) takes the listed IRIs in their new order: an unlisted position follows its current predecessor, an IRI of an item that no longer exists is ignored, and another group's position, a repeated IRI or an IRI that is not a position is a 422 on `componentPositions[i]`. A reorder is not checked against `maxComponents`.
- **One placement rule, `Helper\ComponentPosition\ComponentPositionOrderer`, for insert, move and reorder.** It keeps the longest non-decreasing subsequence of `sortValue − index` with values ≥ 0 (the earliest-ending on a tie, each step taking the earliest predecessor), fills between kept positions consecutively after the earlier one, takes the values just below the first kept one before it, +1 after the last, and starts at 0 when nothing is kept, so it changes the fewest positions and every value ends unique. A new position has no value to keep; a moved one keeps its value when it fits, exactly as in a reorder. The module mirrors the issue's table, so change no expected value without Daniel. Steps are 1.
- **Order is `sortValue`, then `id`**, on `ComponentGroup::$componentPositions` and the position collection; the module compares IRIs, which differ only by id.
- **No lock and no own transaction.** Each ordering write works on the group's `componentPositions` as loaded (ordered by `sortValue`, then `id`) and flushes once, like every other write. A rare concurrent reorder can leave a tie; the next ordering write removes it. Placement is the innermost `state_processor.locator` decorator (60): a written position is placed when it is not in its group's collection yet (new, or moved from another group) or carries an anchor, and is then added to that collection so the next position of the same write sees it.
- **The reorder is a PATCH with no ETag; positions it leaves out keep their place, following their predecessor; clients reconcile from the complete response.** `ComponentGroupOrder` is the one representation of GET, the PATCH body and both responses (no input DTO): `componentPositions` (the only writable field) and `sortValues` cover every position the group lists (`ListedComponentPositions`) in server order, including ones the PATCH left out or another request added; `componentGroup` and `sortValues` are read-only. The order provider serves the PATCH's read and, after the processor's flush, its response.
- A reorder publishes and purges only the positions whose values changed (each is an entity update; the group is not updated and is not published). `ComponentGroupOrderStateProvider` adds the group's and every listed position's IRI to the request's `_resources`, so a position write purges a cached `GET …/order`; there is no normalizer for the order.
- **`POST {component IRI}/move` (#526) is the separate writes in one flush, never a rule of its own.** `ComponentMoveRequestResolver` parses `from`/`to` (422 at `from`, `to`, `from.componentPosition`, `to.componentGroup`…); `ComponentMover` checks the caller is granted each underlying operation's own `security` and `securityPostDenormalize` (the position's `PATCH`, `POST` or `DELETE`, each page data's `PATCH`) through `ComponentMoveAccessChecker`, validates the written position and page data with their whole constraints, reporting violations under `from.`/`to.`, places a position with `ComponentPositionPlacer` (the placement decorator's helper), and flushes once, so `PropagateUpdatesListener` purges and publishes. A position moved into a property is removed directly, never through `OrphanedResourceHelper`, so its component stays. **Never remove a moved position from its old group's `componentPositions`**: the collection has `orphanRemoval`, so Doctrine deletes the position. A draft and its published component count as one (`ComponentCycleDetector::isSameComponent()`), and what `from` holds is what is written, so `DraftComponentReferenceListener` stores the published one. A target property that already holds a component is a 422, never a replace. The response sets `skip_null_values: false` so a property target returns `componentPosition: null`.
- `ComponentPosition.component` is `ON DELETE SET NULL`, deliberately, so dynamic positions survive their fallback. Static positions are removed by `ComponentPositionRemovalStateProcessor` on an API delete only.
- **Nothing stores a reference to a draft that has a published version; a never-published draft is stored as it is** (#520). Publishing a draft of a published component deletes its row, so a reference to it would be emptied by `ON DELETE SET NULL` (or lose its join rows); a never-published draft's first publish keeps the row, so a reference to it becomes live in place. `EventListener\Doctrine\DraftComponentReferenceListener` is the one place this is enforced, on `onFlush` (priority 100, before `PropagateUpdatesListener`), so the API in both modes, fixtures, CLI and direct Doctrine writes all agree, and validation (which judges the class, the cycle detector counting the pair as one) sees the draft unchanged. **Single-join-column associations:** on every inserted entity of any class, and every updated one whose association changed, an owning single-join-column association to an `AbstractComponent` (a position's `component`, a page data component property, a component field such as `related`, an application entity's) holding a draft of a published component is re-pointed at the published component and the change set recomputed. A publishable class's own `associationName` is never re-pointed. **Group owners:** for every scheduled update of a component's `componentGroups`, each group in the insert diff of a draft of a published component that the published component does not already own is moved to the published component (removed from the draft, added to the published component, `computeChangeSet()` on it, the group's `components` updated only when that collection is already dirty, so a clean one is never scheduled). A group the published component owns stays co-owned by the draft: `createDraft()` clones the collection, and that co-ownership is what the admin's draft view reads. So a group is never owned only by a draft of a published component, and naming a draft as the owner resolves exactly as naming its published component. **Watch:** an admin's IRI for a published component that has a draft can resolve to the draft on denormalization, so the module's own published IRI reaches the bundle as the draft; that is the case this listener exists for. The inverse `componentPositions` collections are not maintained.
- **Publishing a draft gives the published component the union of both components' groups** (#520). `PublishableDraftMerger::mergeDraftIntoPublished()` copies properties by reflection on the published class, which never sees a parent's private property, so `AbstractComponent::$componentGroups` is not copied; it is merged explicitly with `addComponentGroup()` for each of the draft's groups. Never replace the published collection with the draft's: a group the published component gained after the draft was made would lose its only owner when the draft row is deleted.
- **`GET {component}/usage` is `ROLE_ADMIN` only** (#531, the operation's `security`, like the orphan report and purge endpoints): anonymous is the firewall's 401, any other user 403, a draft included, before any lookup. It always returns the counts with `locations` (`ComponentUsageMetadataFactory::createWithLocations()`); `create()`, counts only, is for the delete cascade (`OrphanedResourceHelper`). The operation is `private, no-store` (`cacheHeaders` on the operation), because nothing purges it when a placement changes. **The counts are the definition of a use**: one location per counted position (a dynamic position whose fallback is the component included, flagged by `pageDataProperty`) and per page data property, from the same `findByComponent()` rows and `findPageDataComponentMetadata()` matches the counts come from, so the two can never disagree. Never compute the list from a second lookup.
- **`Helper\ComponentUsage\ComponentUsageLocator` answers `renderedOn` in a fixed number of queries, whatever the depth**: it loads the component-owned subgraph as ids (group owners with each draft's published id, positions holding a group owner or a group-owning draft's published component), walks it in PHP with `ComponentUsageGraph` (visited set, a draft owner climbing through its published component), then fetches page owners, layout owners, template page data and page data holding a reached component with one `IN` list each, sized by the answer. Add a step to the walk as data in the graph, never as a query per level. `ComponentUsageLocations` is the one place for order and caps (layouts first by reference, then routed by path, then unrouted by title, untitled last; 50 locations, 20 `renderedOn`, counts exact).
- **A page data is in `renderedOn` only where the fallback actually renders on it** (#541). A dynamic position on the way (the counted position itself, or one holding a component the walk climbs through) is overridden on a page data whose class maps that `pageDataProperty` and holds any component in it; then the walk for that page data does not pass it, so a page data that overrides it is left out, and one that holds the component itself is listed only as its own page data location. A page data whose property is null, or whose class has no such property, renders the fallback, as `ComponentPositionNormalizer` does; the usage is admin-only, so an unpublished override still counts as set, and `allowedComponents` is not applied. Overrides are read only when some walk passes a dynamic position, with one query per page data class (matched exactly, inherited component associations included) that has candidate page data, never per page data; the walk is repeated in PHP once per distinct set of overridden properties. The template itself is always listed.
- **`layout` names one layout, the lowest `reference`, even when a use reaches several through a shared container** (#535, by design): the module shows it as a label, and `renderedOn` is the complete answer for pages.
- **A list inside a DTO that is not an API resource is normalized as a Hydra `Collection`** unless its property carries `#[Context(normalizationContext: ['api_sub_level' => true])]`, as `ComponentUsageMetadata::$locations` does.
- **A component matches a page data property by class hierarchy, never by short name** (#345). `PageDataMetadata::findPropertiesByComponentClass()` uses `is_a()` against the property's Doctrine target, so a property typed `AbstractComponent` or a parent component class holds any subclass. `PageDataProvider::findPageDataComponentMetadata()` is the one lookup behind usage counts (`/usage` and the cascade on delete), `ComponentVoter`'s page data reachability and `PropagateUpdatesListener`'s purge and Mercure fan-out, so a component held only by such a property is used, public only when the page data is on a live route, and propagates to the page data on edit.
- **Publish now is `"publishedAt": "now"`, resolved by the server** (#407). `PublishableNormalizer::denormalize()` replaces the exact string `PublishableNormalizer::PUBLISH_NOW` with the current time (`RFC3339_EXTENDED`, so truncation can only make it earlier, never scheduled) after `unsetRestrictedData()`, so a caller who may not publish still cannot send it, and before the `?published=true` path, where any change is still a 422. Never rely on Symfony's loose date parsing for it: that fallback is deprecated in 8.1 and throws in 9.0. Send a raw body to test the server's `"now"`.
- **A position never exposes a publishable component that is not active to a caller who is not granted** (#492), static or dynamic, and neither does `_metadata.staticComponent`. `ComponentPositionNormalizer` drops the `component` key from its output rather than nulling the entity (#389), so the key is absent, not `null`; the module treats a missing `component` as an empty position. A granted caller still gets the draft swapped in. The manifest follows, because it is built from the normalized position.
- `createdAt` is restored in `TimestampedNormalizer::denormalize()` (#213). `OBJECT_TO_POPULATE` is not always an instance of `$type` (a `PersistentCollection` when denormalizing a collection property), so gate on `instanceof`; an object denormalized into anything that is not an instance of `$type` is new and gets a fresh `createdAt` (a position embedded in a component `PATCH`).

### Orphaned resource report (#190)

| Endpoint | Purpose |
|---|---|
| `POST /_/orphaned_resources/scan` | Refresh. `ROLE_ADMIN`, no body, 202. Dispatches `ScanOrphanedResourcesMessage` on `messenger.default_bus`. **It runs synchronously unless the application routes the message to an async transport**, like the mailer's `SendEmailMessage`; with no bus at all the processor runs the handler itself. |
| `GET /_/orphaned_resources` | `ROLE_ADMIN`. The last stored report: `generatedAt` plus IRI lists `componentGroups`, `componentPositions`, `components`. **404 until a scan has stored one.** `private, no-store`. |
| `POST /_/orphaned_resources/delete` | `ROLE_ADMIN`, 200. Body `{"iris": [...]}` or `{"all": true}`, exactly one (422 otherwise; an empty body never means all). Returns `deleted` (IRIs by kind, cascades included, each once) and `rejected` (`{iri, reason}`, reason `not_orphaned` or `not_found`, in request order). |
| `silverback:api-components:scan-orphaned` (alias `clean-orphaned`) | The scheduled-run path (#348): scans synchronously through `ScanOrphanedResourcesHandler::scanAndCompare()`, stores the report, prints counts per kind (IRIs with `-v`), emails the configured recipients when the result differs from the last alert (`--no-notify` skips it), exits 0. |

- **The bundle reports; the admin chooses what to delete** (#345). Scanning, the command included, never deletes. `OrphanedResourceDetector` is the one definition of an orphan; do not add a second.
- **Deletion trusts only a fresh scan.** `OrphanedResourceDeleter` runs the detector inside the request and deletes only IRIs in that result, never the stored report or the client's list. Anything else is rejected, not an error, so "delete selected" survives a change in between.
- **A delete leaves nothing for the next scan to find** (#351). The cascade lives in `OrphanedResourceHelper`, shared by the API `DELETE` listener and the orphan deleter. A group takes its positions and the components only they use. **A component removed by a cascade** (or deleted as an orphan, `handleRemovedOrphanedComponent()`) takes the groups it owns, recursively, unless an owner not being deleted also has them, and its draft unless that draft is itself in a surviving position or in page data. Owner and "surviving" checks read the unit of work's scheduled deletions. **An explicit API `DELETE` of a published component keeps its draft** (`Publishable\PublishableTest` pins it: the draft is the pending content, and it takes over the positions), so only cascades and orphan deletion remove drafts.
- The orphan deleter removes everything in one flush, so it is one transaction and `PropagateUpdatesListener` purges and publishes as for any write. The response lists what the unit of work deleted, so cascades are reported once. The stored report is refreshed afterwards.
- `OrphanedResourceHelper` has no check-and-remove methods any more; do not reintroduce a second deletion path. Keep the report behind `OrphanedResourceReportStore`.
- **An orphan is anything not linked into the CWA tree**, by reachability, not only at the top (#357). The tree is anchored at pages, layouts and page data component properties; everything else is live only if something live reaches it:
  - a group is live when a page or layout owns it, or a live component does;
  - a position is live when its group is live and it has a component or a `pageDataProperty` (an empty position is always an orphan);
  - a component is live when it is in a live position or in a page data component property;
  - a draft is live when its published version is, or on its own terms. **A draft is never listed**; its published version is judged by its own usage only, and a dead draft's groups are orphans.
  So a position in an orphaned group is an orphan, and so is a component only such positions hold, and the groups it owns, to any depth. A group shared with a live owner, or a component also placed on a live page or held by page data, is not. **A cycle nothing live reaches** (a component in a group it owns) is an orphan, including a cycle with no other link at all. An application's own Doctrine relations to a component do not count as use.
- **`OrphanedResourceDetector` is three DQL queries, whatever the site size and however deep the chains.** It loads only the subgraph that can hold orphans, as ids: groups with no page or layout owner with their component owners; positions in those groups plus every empty position; components in no position of a page- or layout-owned group and in no page data property, with each draft's published id. Liveness is then a worklist in PHP from what those rows show is anchored, so there is no per-level query, no parameter list and no recursion in SQL, and cycles terminate because each node is marked once. Do not turn it into an iterative query per level: that needs `IN (:ids)` lists that hit parameter limits and misses cycles nothing seeds. Page data component properties come from Doctrine metadata (owning single-join-column associations on `AbstractPageData` subclasses to an `AbstractComponent`, not inherited) and become `NOT IN` subqueries; each publishable class's own association becomes a scalar `(SELECT IDENTITY(…) …)` column. Names come from Doctrine, so the table prefix is honoured. Memory grows with the component-owned part of the site (all nested content), not with the whole site.
- **Never hydrate the orphaned components.** A published component's inverse one-to-one `draftResource` is loaded eagerly, so hydration costs one query per orphan. The query selects `c.id` and a `CASE WHEN c INSTANCE OF … ELSE … END` type (deepest class first; DQL requires the `ELSE`), and IRIs come from `getReference()`, which queries nothing. Read ids with `getResult()`, not `getScalarResult()`: only the former converts `c.id` to the `Uuid` that `getReference()` must be given.
- Verified identical on SQLite, MySQL 8.0.46, MariaDB 10.11.19 and PostgreSQL 16.15 on a fixture with nested chains, shared components and groups, page data, drafts and both cycle shapes (#357).
- **Delete all agrees with the scan.** Everything the cascade removes is listed, apart from drafts, so `{"all": true}` deletes exactly the listed groups and positions, the listed components plus their dead drafts, and a fresh scan is empty. `OrphanedResourceDeleterTest` and `Orphan\OrphanedResourcesCascadeTest` pin it.
- **The report lives in the database** (#348), one row of `OrphanedResourceReportRecord` (`_acb_orphaned_resource_report`, fixed id 1) updated in place, so every pod reads the same report and it survives deploys. Never back it with `cache.app`: the template's pool is per-pod filesystem. The same row holds the **last alert** (`last_notified`, nullable JSON: the report as of the last successful notification evaluation), written only by `markNotified()` and read by `fetchNotified()`. `save()` never touches it. No other history is kept. Nothing is held on a shared service, so no `kernel.reset`.
- **`generatedAt` has microsecond precision**, stored as an ISO 8601 string (`OrphanedResourceReportRecord::GENERATED_AT_FORMAT`) and serialized in the same format, because the module detects a finished scan by a changed `generatedAt` and DBAL datetime types drop fractions.
- **Notifications (#348, #355):** `OrphanedResourceNotifier` emails `orphaned_resources.notify.recipients` when `OrphanedResourceReportChange::hasChanged()`: the IRI sets per kind differ from the **last alert**, not from the report the scan replaced (order ignored). With no last alert yet, a result counts as a change only if it has orphans. The email carries counts per kind, IRIs new since the last alert, a count of those no longer orphaned since then, and a link to `notify.admin_page_path` (default `/_cwa/orphaned`) on `user.email_links.default_origin`, through `RefererUrlResolver::getDefaultOriginUrl()`, which ignores any request origin. No usable default origin sends the email without the link and logs a warning.
- **Only the command notifies.** The HTTP scan and the refresh after a bulk delete call `scan()`, never the notifier: the admin is already looking. They replace the stored report but **never touch the last alert**. The recipients are not necessarily the admin who scanned, so an admin's scan must not absorb a change the alert exists to report (#355); comparing against the replaced report did exactly that.
- **When the last alert advances** is `OrphanedResourceNotificationResult::advancesBaseline()`, applied by `ScanOrphanedResourcesHandler::recordNotification()`: after `Sent`, and after `Unchanged` (nothing to send, so an old baseline cannot re-alert forever; a first empty result sets it). **Not** after `Failed`, so the next run emails again, and **not** for `NoRecipients` or `--no-notify`, where nothing was evaluated.
- **No recipients means off**; there is no `enabled` flag. Null (e.g. an empty `%env(default::MAILER_EMAIL)%`), an empty string and an empty list all mean no recipients, and must never stop the scan itself (#365). `recipients` is a list or one comma-separated string, so a plain `%env()%` can supply it (an array node rejects an env placeholder). Each recipient is a bare address or `Name <address>` (the template's `MAILER_EMAIL` form), parsed with `Address::create()`, never `new Address()`, which takes a bare addr-spec only (#361). A string is split by `Utility\EmailRecipientList::split()` on commas outside double quotes, so `"Smith, Jane" <jane@example.com>` is one recipient; an unquoted name with a comma is split and rejected, as RFC 5322 requires the quotes. Config validates literal addresses; env values are validated again at send time, where an invalid address fails the notification.
- **A failed notification never fails the scan.** The report is saved before sending. The send uses the user emails' semantics: a `TransportExceptionInterface` is logged at error as a `MailerTransportException`, and the command prints that the notification failed and exits 0.
- **The GET must stay `private, no-store`.** A new scan writes `OrphanedResourceReportRecord`, which is not an API resource, so nothing purges a shared-cache copy.
- The POST needs `read: true` like the purge endpoints. Anonymous POST 401 in the test app is the firewall's; the `@loginUser` 403 is the operation's own security.
- **`silverback:api-components:delete-stored-files <filesystem> [<path>]`** (#477) deletes every file under a path of a `FilesystemProvider` filesystem; no path needs `--all`. Its guard, `--only-if-value` + `--matching`, takes the value from the caller because an adapter's path prefix is private to Flysystem: the template passes its `GCLOUD_PATH_PREFIX`, so a review app deployed with no prefix can't empty the bucket. Keep the guard checked before the filesystem is touched.

### Orphaned file report (#371)

The stored-file counterpart of the orphaned resource report, with the same shape: `POST /_/orphaned_files/scan` (202, `ScanOrphanedFilesMessage` on `messenger.default_bus`, synchronous unless the application routes it to an async transport, which a large bucket justifies), `GET /_/orphaned_files` (404 until a scan, `private, no-store`), `POST /_/orphaned_files/delete` (`{"paths": [...]}` or `{"all": true}`, exactly one, 422 otherwise), all `ROLE_ADMIN`, and `silverback:api-components:scan-orphaned-files` (counts, `-v` lists, exit 0, never deletes). There is no notification email yet.

- **Report:** `orphanedFiles` and `unknownFiles` are `{adapter, path}` per filesystem holding the file; `missingFiles` is `{resource, adapter, path}` per uploadable row whose stored path has no object. **A missing file is only reported, never deletable**: it has no object and its row still references it, so a delete request for it is rejected as `not_found`.
- **Only a file the bundle wrote can be orphaned.** An unreferenced file is **orphaned** when its basename matches a name the bundle generates (`StoredFileNameMatcher`: the #194 `<slug>-<8 lowercase hex>[.<ext>]` of `UploadableFileManager::tokeniseFilename()`, or the version 4 UUID name `UploadableNormalizer` gives a data-URI upload) **or** an `_acb_imagine_cached_file_metadata` row exists for its path, with any filter (`FileInfoRepository::findPaths()`, one scalar query). Otherwise it is **unknown**: reported, never deletable. `{"all": true}` skips it and naming it is rejected as `unknown`. **Change the matcher whenever the stored-name scheme changes**: `StoredFileNameMatcherTest` runs real outputs of `tokeniseFilename()`, `persistFiles()` and `processClonedUploadable()` through it. The minimum age and exclusions apply before the classification, so an excluded or too-new file is in no list.
- **A file info row is written when a resource holding the file is normalized** (`UploadableNormalizer` → `MediaObjectFactory::create()`, including the response to the upload itself), never while building a manifest, and removed by `deleteStoredFile()`. A pre-#194 file that no API response ever included (fixtures, direct `persistFiles()`) has none, so it is unknown.
- **Scope is the uploadable fields' filesystems and prefixes only.** `StoredFileLister` walks each adapter's field prefixes (the outermost of nested ones; a prefix may end mid-filename), shallow listing per directory so an excluded directory is never listed. A field with no prefix claims the whole filesystem, because an adapter registered with `silverback.api_components.filesystem_adapter` exists for uploads.
- **Anything else on those filesystems must be excluded, or it is reported.** Every `FlysystemCacheResolver` tagged `liip_imagine.cache.resolver` excludes `<cachePrefix>/` automatically; an empty cache prefix excludes everything, so nothing is reported. Anything else the application stores there goes in `orphaned_files.excluded_paths` (path prefixes). **Exclusions and references apply across every scanned filesystem**, not per adapter, because two aliases can point at the same storage (the test app's `local` and `public_url_local` do). That can hide an orphan; it can never report a file in use.
- **Referenced = any row of any uploadable class and field stores the path**, drafts included, compared after Flysystem's path normalisation. Read as scalar DQL, one query per concrete uploadable class (all its fields at once, `NOT INSTANCE OF` its subclasses), never by hydrating. A missing-file candidate not in the listing is confirmed with `fileExists()`, since it may sit outside the scanned paths.
- **Minimum age** (`orphaned_files.minimum_age`, seconds, default 3600): an upload is written before its row is flushed, so a younger file is never reported. The age comes from the listing's `lastModified`, else `lastModified()`; a file whose age cannot be read is not reported.
- **Deletion trusts only a fresh scan**, as for resources: `OrphanedFileDeleter` scans inside the request and deletes a requested path on every filesystem that scan reports it on, through `UploadableFileManager::deleteStoredFile()`, which also removes its imagine variants and `_acb_imagine_cached_file_metadata` rows. Rejected reasons, in request order: `unknown` (in the fresh scan's `unknownFiles`), `not_orphaned` (exists on a scanned filesystem), `not_found`, and `delete_failed` (a Flysystem `FilesystemException`, logged at error; the other paths still proceed and the file stays in the report).
- **The imagine cache is cleaned only with its source, never scanned on its own.** A variant is keyed by its source path in liip's resolver store, which the bundle does not own the layout of in general; variants whose source was deleted before this report existed are left behind.
- **The stored report after a delete is the delete's own fresh scan minus what was deleted**, not a second listing, because a listing is the expensive part.
- **The report lives in `_acb_orphaned_file_report`** (`OrphanedFileReportRecord`, fixed id 1, updated in place), never `cache.app`. Upgrade step: generate and run a migration. `generatedAt` uses the resource report's microsecond format.

**Invalid files (#388)** are the fourth list of the same report, from the same scan: `invalidFiles` is `{resource, field, adapter, path, violations}` per present referenced file that breaks its field's **current** constraints. Like a missing file it is only reported; nothing modifies or deletes it, and a missing file is never checked.

- **The constraints are those of the groups publishing would validate, on the `UploadableField` property** (`file`, not the stored `filename`) (#457): `Default` plus `getPublishedValidationGroups()` for a row of a publishable class whose publication date is set (scheduled included, as `PublishableValidator` uses `hasPublicationDate()`), `Default` alone for a draft or a class that is not publishable. The publication date is one more column of the scalar reference query, never a hydration. A constraint passed to the validator directly is validated once per group it is in, so `StoredFileConstraintChecker` collects each constraint once and validates it in the first given group it belongs to. They are read from the application's validator metadata by `StoredFileConstraintChecker`, and validated against a `StoredFile` by a private validator whose `StoredFileConstraintValidatorFactory` sends `File` and `Image` to `StoredFileConstraintValidator`, any `Composite` (`When`, `Sequentially`, …) to the application's `validator.validator_factory`, and **skips every other constraint**: they would validate an uploaded file the scan does not have.
- **`StoredFileConstraintValidator` must give the messages and codes Symfony's `FileValidator`/`ImageValidator` give the same file on disk.** `StoredFileConstraintValidatorTest` runs each option against both; extend its matrix when you support an option. Checked: empty, `maxSize`, `mimeTypes`, and every `Image` dimension, pixel, ratio and orientation option (SVG skips width, height and pixels, as Symfony does). Not checked: `extensions`, filename length or charset, `detectCorrupted` (it decodes the image).
- **A `When` expression sees `value` as the `StoredFile`** (`getMimeType()`, `getSize()`, `getFilename()`, `getPath()`) and `this` as null. An expression calling anything else throws and fails the scan, as configuration errors do.
- **File info first, the object only when there is no row.** The original's `_acb_imagine_cached_file_metadata` row (filter null) supplies mime, size and dimensions, loaded with one query and only when some referenced field has constraints. With no row, `StoredFile` asks Flysystem for mime and size, and for dimensions copies the stream to a `tmpfile()` and calls `getimagesize()` on it, lazily, so only an `Image` option with dimensions reads the object. **An SVG's size is read from the object even when it has a row** (#457), with Symfony's `ImageValidator::getSvgSize()` rules copied exactly: `width`/`height` with length units converted to pixels (int when integral, else float), a missing or unparseable one (a percentage, `em`) taken from the `viewBox`, else no size. The row's SVG dimensions come from `MediaObjectFactory`, which reads the attributes as integers only. Symfony read units only from 7.4.x/8.x patch releases of 2026-06; `StoredFileConstraintValidatorTest` skips the units asset on an older validator (the lowest-dependency legs). **Never decode the image (GD) to check it.** A `FilesystemException` while checking is logged at warning and that file left out.
- The deleter's fresh scan checks constraints too, and its stored report keeps `invalidFiles` as scanned.

### Filters (#289, #237)

Route, Layout and Page declare `QueryParameter`s: `search` = `FreeTextQueryFilter(new OrFilter(new PartialSearchFilter()))`, `order[:property]` = `SortFilter`, Page `isTemplate` = `ExactFilter` + `BooleanQueryValue` (casts to `'1'`/`'0'`; an array of booleans binds `false` as `''`). `OrSearchFilter` is removed.

- **Never use `orWhere()` in a filter.** It ORs against the whole accumulated WHERE and discards publication, draft and ancestor predicates. `OrFilter` must always be wrapped in `FreeTextQueryFilter`. Apply a filter's clauses as one `andWhere(Orx)`.
- `PartialSearchFilter` inner-joins nested properties, which removes rows inside an OR search, so `layout.reference` was left out of the Page search.

### API Platform and Symfony compatibility

- **API Platform `^4.4 || ^5.0`, with no version branches in code** (#287). Nothing in `src/` may use a 5-only API. Denormalization error statuses differ between versions, deliberately not normalised; a test asserting one must hold on both.
- All AP metadata is in PHP attributes; `prependApiPlatformConfig()` registers mapping directories. Serializer groups use `Symfony\Component\Serializer\Attribute\Groups`.
- `RoutingPrefixResourceMetadataCollectionFactory` prefixes `AbstractComponent` subclasses with `/component/`, `AbstractPageData` with `/page_data/`, and other bundle classes with `/_/`. It **combines** with an existing `routePrefix`, so never set one on such a class.
- `ApiPlatformCompilerPass` **appends** AP's default `exception_to_status` entries, read from AP's config tree, because the bundle's prepended map replaced them (#293). Appended, so an application's more specific mapping wins.
- `/me` keeps `@type: User` and `@context: /contexts/User`.
- 4xx/5xx from AP's exception handler are `application/problem+json`.
- Symfony 8 constraints need named arguments (`new Count(min: 1)`).
- Prefer `?string = null` with a nullable column, so null reaches `NotBlank` on every Symfony version.
- **Every API-writable `string` column needs an `Assert\Length` whose max is its column length** (255 by default), in every validation group its other constraints run in (#427). SQLite ignores `VARCHAR` length, so the test app saves an over-long value that MySQL and PostgreSQL reject with a 500. `StringColumnLengthTest` checks every `string` field in `src/Entity`; a column only the server writes goes in its exemption list.
- Set `$context['api_sub_level'] = true` when normalising a sub-object, or `PartialCollectionViewNormalizer` injects `view` into arrays whenever the URI has a query string.
- `ApiResource::getOperations()` is `Operations<HttpOperation>`. Do not annotate its items as `Operation`, which hides the HTTP methods.
- ORM-only calls (`getUnitOfWork()`, `ClassMetadata::getFieldValue()`, `getAssociationMappings()`) need the manager narrowed to `EntityManagerInterface`; `getManagerForClass()` returns the Persistence `ObjectManager`.
- `Request::getContentType()` was removed in Symfony 7.0 (use `getContentTypeFormat()`), and Lexik 3 removed `JWTManager`'s user identity field methods. A call to either is an undefined-method Error.
- The bundle's `UserPasswordValidator` decorates Symfony's for the whole application, so the token user may be any `PasswordAuthenticatedUserInterface`, not only an `AbstractUser`.

### API Platform request lifecycle (#368)

The bundle does not set `use_symfony_listeners`. API Platform's default (`false`, `MainController` and the state provider/processor chain) is what CI runs on every leg. One `functional` CI leg runs with it `true`, because an application may still set it. **Never bind bundle behaviour to `EventPriorities::*` or `kernel.request`/`kernel.view`.** In controller mode those listeners never see the resource, and MCP tool calls run only the chain. Decorate a service that exists in **both** modes instead:

| Decorate | Runs where the old listener ran | Current decorators (priority) |
|---|---|---|
| `api_platform.state_provider.read`, negative priority, so it wraps the `security` access checkers (0, 10) | `POST_READ`, `PRE_DESERIALIZE` | deny access (-20), publishable merge (-30), component usage (-40), upload and download (-50), resource version (-60) |
| `api_platform.state_provider.deserialize` | `POST_DESERIALIZE` | publication date guard (-10) |
| `api_platform.state_provider.validate` | `POST_VALIDATE` | route generation (-10) |
| `api_platform.state_processor.locator`, the persist/remove call | `PRE_WRITE` before the inner call, `POST_WRITE` after it | version conflict (5), publishable (10), user emails (15), uploadable (20), delete cascade (30), position removal (40), route redirects (50), position placement (60) |
| `api_platform.state_processor.serialize` | `PRE_SERIALIZE` | form (10), collection (20) |

- **Never decorate `state_processor.write` or `state_*.main`.** In controller mode, `write`'s inner call is serialize and respond, so its "after" runs after serialization. The `main` services do not exist in listener mode.
- On a service, a lower priority is further out: its "before" part runs earlier and its "after" part later. The priorities above reproduce the old listeners' order. `StateDecoratorServicesTest` pins each decorator's target and priority.
- A decorator reads the request from `$context['request']` and returns the resource. When it replaces the resource, it also sets the request's `data` attribute: listener mode's `PlaceholderAction` returns that attribute, and `kernel.response` listeners read it. Test for `HttpOperation` and use `$operation->getMethod()`, not the request method.
- **No custom `controller` on an operation.** In controller mode an operation with its own controller bypasses the whole chain. Mark it with an extra property and handle it in a decorator, as upload and download do.
- An operation added by a metadata factory takes the controller of the operation it copies, and is named after its key (`withName()`). A provider matches the operation by `$operation->getName()`.
- Response headers stay plain `kernel.response` listeners (`Expires` and `valid-to-publish`, `Vary: path`, form 422 and canonical `@id`, cache headers). They read `_api_resource_class`, `_api_operation` and `data`, which both modes set.
- **`src/EventListener/` holds only classes registered as listeners.** A decorator's logic that other code also calls is a helper under `src/Helper/<Area>/` with a `silverback.api_components.helper.*` id: `PublishableDraftMerger`, `UserWriteNotifier` (also called by `EntityPersistFormListener` and `EmailAddressManager`), `CollectionPopulator`. Decorators and helpers are `final`; their unit tests build real helpers over stubbed collaborators (`tests/Helper/Publishable/PublishableDatabaseTrait` gives a real in-memory entity manager) rather than mocking them.
- The uploadable write decorator never deletes files on `DELETE`; `UploadableFileDeletionListener` owns that after the flush (#370).
- Decorators act only on an `HttpOperation`. Whether MCP tool calls get the same hooks is #333's decision.
- The test kernel reads `API_PLATFORM_USE_SYMFONY_LISTENERS` (`0`/`1`; unset leaves the default) and uses a separate cache directory for each value. It runs with `debug: false`, so it never rebuilds the container when the setting changes.

### Dependency injection conventions

- Services use `silverback.api_components.*` ids with FQCN aliases, **except** AP state providers/processors referenced by class on an operation and `controller.service_arguments` actions. Those keep the **FQCN as primary id**, or AP throws `ProviderNotFoundException` and argument injection fails.
- **Never rely on autoconfiguration, registration order or decoration inference in a bundle.** Tag and order explicitly; several definitions use `->autoconfigure(false)`.
- **Services holding request-scoped state must be tagged `kernel.reset`** explicitly, or scope the state with a `WeakMap`. FrankenPHP worker mode keeps services alive across requests. Add each such service to `tests/DependencyInjection/ServicesResetterTest.php`.
- **A class that implements `ResetInterface` must be tagged `kernel.reset`, on every service of it, children of a parent definition included** (Symfony never inherits tags from a parent). `ResetInterfaceServicesTest` loads every bundle config file and fails on any that is not. Implementing the interface alone resets nothing.
- **A map keyed by objects that live for one request (entities, `_metadata`) is a `WeakMap` and is also reset** (#447). The `WeakMap` alone is not enough when a value can reference its key, as `ResourceMetadata`'s violations reference the resource. Never key by `spl_object_id`: it holds nothing and is reused once the object is freed. `Page\WorkerModeMemoryTest` sends requests through one kernel and asserts both maps are empty after each services reset.
- **API Platform resets its skolem IRI converter itself from 4.4.5 and 5.0.4** (api-platform/core#8681), which is why the bundle requires them: it keeps every anonymous object it gives a `/.well-known/genid/` IRI (each `_metadata` object) until a services reset. `Page\WorkerModeMemoryTest` pins it.
- Optional collaborators (logger, purger) are wired as `new Reference(..., NULL_ON_INVALID_REFERENCE)`.
- **Config nodes:** never put `isRequired()` on a child of a node with `addDefaultsIfNotSet()` or `canBeDisabled()`. The default is inserted without finalising, so the check never runs (#214). Give the child a real default or make the parent required. Use `->validate()` for invalid combinations. Env placeholders skip node validators, so validate again at run time.
- `make:rename-component` generates through `doctrine.migrations.dependency_factory` and reads table names from `ClassMetadata`. **Never `LIKE`-match an IRI in a `json` column** (slashes are escaped). AP's `getIriFromResource()` returns a `/.well-known/genid/` blank node, not an exception, for a non-resource class.

## CwaFixtureBuilder

A fluent API over Doctrine fixtures. `AbstractCwaScaffold` implements `FixtureInterface` and is auto-tagged; implement `build(CwaFixtureBuilder $cwa)`. Unit tests: `tests/Fixture/CwaFixtureBuilderTest.php`. Fixture loads must keep purge-and-reload.

```
CwaFixtureBuilder
  ->layout(ref, uiComponent, ?uiClassNames): LayoutBuilder   (deduped by ref; prepends 'CwaLayout')
  ->page(ref, uiComponent, layout, ?route, ?routeName, isTemplate=false, ?Closure, ?uiClassNames): PageBuilder  (prepends 'CwaPage')
  ->pageData(AbstractPageData, ?template, ?route, ?routeName, ?Closure): PageDataBuilder
  ->component(AbstractComponent): ComponentBuilder
  ->getRoute(routeName): Route                               (a route named in this load, else an existing route with that name)
  ->redirect(path, to: routeName|PageBuilder|PageDataBuilder, ?name): static  (a redirect Route to a named route or a builder's route; registered by its own name, derived from the path and suffixed -1, -2… when taken)
  ->afterRoutes(Closure(CwaFixtureBuilder)): static          (runs once, after routes exist and before positions are created)
  ->persist(object): static                                  (queued until flush() when called before it)
  ->publish(object, ?at: DateTimeInterface): object          (sets the publishable date now, or to `at`, in the class the mapping uses; returns the object; never persists)
  ->asset(sha256, ?name): UploadedFile                      (a copy of a fixture asset from the store, under its manifest name or `name`; only while an AbstractCwaScaffold loads)
  ->getSummary(): CwaFixtureSummary, ->reportSummary()       (what the last load created, kept and skipped)
LayoutBuilder    ->group(name, allow: [], ?Closure, ?locationReference, ?max): GroupBuilder, ->uiClassNames(...)
PageBuilder      ->title(), ->metaDescription(), ->uiClassNames(), ->group(name, ?Closure, ?locationReference, allow: [], ?max), ->liveAt(?DateTimeImmutable), ->withoutRoute(), ->reachableWithoutRoute(bool = true), ->redirectTo(routeName), ->nested(Closure): self, ->getRoute()
PageDataBuilder  ->liveAt(?DateTimeImmutable), ->withoutRoute(), ->redirectTo(routeName), ->nested(Closure): self, ->linkRoute(property, routeName|page:), ->linkIri(property, ?key, page:|layout:|pageData:|route:), ->onRoutesCreated(Closure(array<PageBuilder>)), ->getRoute()
ComponentBuilder ->uiComponent(suffix), ->uiClassNames(...), ->group(name, allow: [], ?Closure, ?locationReference, ?max), ->linkRoute(property, routeName|page:), ->linkIri(property, ?key, page:|layout:|pageData:|route:), ->draft(AbstractComponent)
GroupBuilder     ->add(AbstractComponent, ?sort), ->pageDataPosition(pageDataClass, propertyName, ?sort)
```

- **Routes:** an explicit `route:` creates that path. With no `route:`, a non-template page is generated from its title, and a template page gets none. A nested page is generated under its parent, and **a parent with no route throws `UnroutedParentException`**, so pass an explicit `route:`. A page or page data with no `route:` and no title gets no route, nested or not, and route generation is never called for it; its children with a generated route then throw `UnroutedParentException`. A title that slugifies to nothing still reaches `RouteGenerator` and fails the load with its 422. In an `--append` load, untitled page data with no `route:` is identified like `withoutRoute()` page data (created only with its template or parent).
- **Flush phases:** persist layouts, pages, page data, and components that own groups with their groups when the scaffold has no `nested()` closure → flush → run `nested()` closures, to any depth (a closure a nested closure declares runs in the same pass), and process the pages, page data **and component builders** (all of them, when there are closures), groups included (#424) → flush → `RouteGenerator` breadth-first, parents first, then `liveAt`, redirects and `redirectTo()`s → flush → resolve `linkRoute()`s, then `onRoutesCreated` and `afterRoutes` callbacks → flush → positions, component builders with no groups, and drafts → final flush. Each phase flushes only when it did something; the unit tests pin those counts, so do not add an unconditional flush.
- **A component that owns groups is persisted after the `nested()` closures whenever the scaffold declares one**, and in phase one only when it declares none, so the flush counts of a flat scaffold are unchanged. A component declared outside a closure and placed only in a nested page is judged against every placement: in an `--append` load, its placement in a kept group skips it instead of creating a duplicate.
- **`linkRoute(property, routeName)` is how a component or page data references a route** (#452): it resolves through `getRoute()` before the callbacks run, so they see it, and again after them, so a `linkRoute()` declared inside `afterRoutes()` or `onRoutesCreated()` is applied too. Each builder's links are applied once, counted per builder, so a callback that sets the property itself is not overwritten. It adds no flush (an already persisted target is written by the next flush that runs). An unknown name throws: it is a bug in the scaffold. It is ignored for a component that is skipped and for page data that was not created. A component that owns groups is still persisted in phase one, because its groups need an owner, so its `linkRoute()` column must be nullable. `getRoute()` is otherwise valid only after route generation, so `afterRoutes` remains for anything else that needs a route.
- **`linkIri(property, key:, page:|layout:|pageData:|route:)` writes the IRI of a site entity into a field** (#452), e.g. `->linkIri('defaultQueryParameters', key: 'parentPage', page: 'blog')`: the whole value with no `key`, else the value at that key or key path (`key: ['filters', 0, 'page']`), creating missing keys. Exactly one target, named as scaffolds name things: a page or layout by reference (a declared one, else the database's), a route by name, page data by its route's name. It is resolved with `linkRoute()`, in the same calls, applied once per builder, adding no flush, skipped for a skipped component and for page data not created, and writes the IRI converter's form (with the import prefix). An unknown target, a key into a value that is not an array, or a property that cannot hold the IRI throws naming `linkIri()`.
- **`redirectTo(routeName)` on a page or page data makes its own route redirect** (#461), for a URL that is both a page and a redirect (a home page that forwards to a section). `$cwa->redirect(path, to:)` is a separate route with no page; the two are not interchangeable. It is applied in the route phase, after `$cwa->redirect()` routes exist and before its flush, so it adds no flush, and again after the callbacks, so one declared in a callback or after a flush is applied by the next flush. It names any route the load or the database knows, and an unknown name throws naming the page or page data. A redirect to its own route throws. Only a route created in this load is changed: kept page or page data, and a route skipped as `path in use`, are left alone. A page or page data with no route of its own (a template, `withoutRoute()`, untitled) throws naming `redirectTo()`.
- **A `PageBuilder` or `PageDataBuilder` can stand in for a route name** (#471): `linkRoute(property, page: $builder)` (exactly one of `routeName` and `page:`), `redirect(path, to: $builder)`, and `linkIri()`'s `route:`, as well as `page: $pageBuilder` and `pageData: $pageDataBuilder` for the entity's own IRI. It is resolved with the named form, in the same calls, adding no flush, to the builder's `getRoute()` (a kept entity's existing route), else the route at its declared `route:` path when that path was in use, as its `routeName:` is. A builder with neither (a template, `withoutRoute()`, untitled) throws, naming the caller and the page. The generator keeps writing route names.
- **Every route the builder creates or keeps is registered by its own name**, as well as by `routeName:`, so `getRoute()` and `redirect(to:)` can name a route whose name was derived or generated. A kept or path-in-use route with no `routeName:` is also registered under `RouteName::fromPath()` of its path when that name is free: a generated scaffold leaves `routeName:` out when it equals the derived name, so an `--append` load into a database whose route at that path is named otherwise (`about-1`) must still resolve `linkRoute('route', routeName: 'about')`.
- **`nested()` adds a closure; it never replaces one.** Each call is run in order in the same pass, so a developer adds a child with one more `->nested($this->childPage(...))` line.
- **An unresolvable route name says who asked for it**: `linkRoute()` names the owner class and property, `redirect(to:)` the redirect's path, and both list the route names registered in this load. A `linkRoute()` property that cannot hold a `Route` throws naming `linkRoute()`. Only a direct `getRoute()` keeps the "did you call flush()" hint.
- **A kept group's scaffold positions are counted in the summary** (`skipped N positions (group kept)`) and the notice names the group and its owner (`the page \`home\``), so a component added to an existing group is never dropped silently.
- **`ComponentBuilder::draft()` links the draft at once** (the publishable `associationName`) and persists it in the positions phase, skipped as `linked to skipped content` when its published component is. `publish()` and `draft()` need the `PublishableAttributeReader` (the builder's last constructor argument) and throw `\LogicException` for a class that is not publishable. Both go through `CwaFixtureBuilder` (a `ComponentBuilder` is given its `linkDraft` closure), so there is one check and one property accessor.
- **A draft of a published component given to `GroupBuilder::add()`, a page data component field or a component field is stored as its published component** (#520), by `DraftComponentReferenceListener` at flush, not by the builder; the draft is still persisted and linked. **A group declared on such a draft (`$cwa->component($draft)->group()`) is created for its published component**, named after the published component's IRI (`publishedGroupOwner()`), as the module names a group's location. `GenerateFixturesRoundTripTest` pins each.
- `PageBuilder::group()` takes `allow:` and `max:` last so existing positional closure calls keep working. `max:` sets the group's `maxComponents` only when the builder creates the group (a kept group is untouched), and the builder does not enforce it: fixtures bypass validation, as for `allow:`.
- `onRoutesCreated` may only mutate entities already persisted (set on the page data before `->pageData()` so phase one cascades them); it never calls `persist()`.
- The builder handles timestamping, persisting, dedup of layouts/pages and groups, position sort values (from 0, in steps of 1, as the API orders a group), bidirectional links and parent propagation. `allow:` takes class names and resolves collection IRIs.
- **Every entity the builder persists through `persistWithAssociations()` is timestamped there**, whether it came from a builder, `persist()` or the walk of owning associations (a component held only in a page data field), when it is `#[Timestamped]` and new: not yet managed, or scheduled for insert by a cascade. An entity already in the database keeps its dates. Groups, positions and routes are persisted with `manager->persist()` directly and timestamp themselves; anything new persisted that way must too.
- `Route.name` is unique. A redirect's derived name is made unique against the database and every route the builder created, as `RouteGenerator` does. A redirect `name:` already given to a route in the same load throws, naming that route, including when the redirect's path already exists (#350); it used to re-point the name at the route at that path.
- A page or page data with no explicit `route:` gets a generated one unless `->withoutRoute()` is set; an explicit `route:` wins over it. `generate-fixtures` emits `->withoutRoute()` for page data and non-template pages that have no route.
- **A fixture load propagates nothing** (#460). While `doctrine:fixtures:load` runs (any fixture, `--append` included), `PropagateUpdatesListener` skips `onFlush` and `postFlush`, so nothing is serialized for Mercure and no per-write purge is sent: serializing an uploadable generates every imagine variant not stored yet, which for a real site's images took gigabytes in one process. `EventListener\Console\FixtureLoadListener` tracks it from `console.command`/`console.terminate` as a stack, so a command nested in a load neither ends it nor flushes, and only the terminate that ends the last running load flushes the whole HTTP cache once through `HttpCacheFlusher` (no Souin purger: says nothing was flushed; a failed flush is logged at error and never fails the load) and, with imagine enabled and exit 0, tells the developer to run `imagine:generate`. Tagged `kernel.reset`. **Console events fire only through `Application::run()`**: a load started with `Command::run()` (as `runConsoleCommand()` does) is not detected, so test it with `runApplication()`.

### Loading into a database that already has content (#319)

`doctrine:fixtures:load --append` creates only what is missing and never modifies, reorders or duplicates what exists; editors own it. The builder cannot tell whether the database was purged, so it **always looks up before creating** and there is no mode flag. On an empty database every lookup misses and behaviour is unchanged. Tests: `tests/Functional/Fixture/AppendTest.php`, `tests/Fixture/CwaFixtureBuilderAppendTest.php`.

| Scaffold item | Identified by | When it exists |
|---|---|---|
| Layout | `reference` | reused, fields untouched |
| Page | `reference` | reused, fields and route untouched; its `routeName` resolves to the existing route |
| Page data | route path: the explicit `route:`, else `RouteGeneratorInterface::generatePath()` (parent route path + title slug, no conflict suffix) | reused when that route belongs to page data of the same class |
| Page data with `withoutRoute()`, or with no title and no `route:` | nothing | created only when its template page or its parent is created in the same load; otherwise skipped as `unidentifiable` |
| Group | its reference as built (`name_<owner IRI>` or `name_<locationReference>`) | reused and linked to the owner if needed; **none of its positions or components are created**, including ones new to the scaffold, since components have no identity |
| Explicit route of a new page or page data | path, or name | the entity is created without a route and the route is left alone (`skipped route (path in use)`); the `routeName` resolves to the route at that path |
| `redirectTo()` of a page or page data | its own route | applied only to a route created in this load; a kept route, or one skipped as `path in use`, keeps its redirect |
| Redirect | path, or its `name:` | kept and registered under its name; a `name:` that belongs to another path is `skipped route (name in use)` and registered to that route |

A redirect's name registers to whatever route holds its path or its name, whether or not that route is a redirect or points at the same target (#350). Path and name are the identity, and editors own the route: a redirect an editor moved keeps its name, and a URL an editor turned into a page is still where the redirect led. Registering nothing would not help either. For a name held by another route, `getRoute()` falls back to that route by name anyway, and for a free name a later reference would throw and fail the whole load over existing data.

- **Anything reached only through a skipped subtree is not created.** The builder keeps a set of skipped scaffold objects: the scaffold copies of kept entities and everything new they reference, and every component in a kept group (recursively through component-owned groups, including components added to the group later in `afterRoutes`). `persist()`, positions and component builders check whether the object reaches a skipped one through owning associations before persisting it. So a generated scaffold's draft, whose `publishedResource` is a component in a kept group, is skipped rather than persisted with a duplicate of its published component. **Never persist a scaffold object without that check**: `persistWithAssociations()` walks owning associations and would write the whole skipped subtree.
- `persist()` called before `flush()` is queued until the page and group decisions exist; called during `flush()` (in `afterRoutes` or `onRoutesCreated`) it runs at once.
- The flush phases, their flush counts, `onRoutesCreated` and #245 are unchanged. Children of kept page data are nested under the existing entity and generate under its route; if that parent has no route, generation still throws `UnroutedParentException`. `onRoutesCreated` is not called for page data that was kept or skipped. A builder's `getRoute()` returns the existing route for kept pages and page data.
- A page data whose natural path belongs to something else is created and gets a suffixed route, so a second append creates it again. Give such page data an explicit `route:`.
- **Report.** `AbstractCwaScaffold::load()` calls `reportSummary()`, which writes `CWA scaffold: created …; kept …; skipped …` to the running command's output and logs it at `info`. Each kept or skipped entity is logged at `notice`, created ones at `debug`. The output comes from `ConsoleOutputListener`, which holds the output of the running console command (`console.command`/`console.terminate`, a stack for nested commands, `kernel.reset`). The fixtures executor's own logger is private to the executor and a Monolog console handler shows only `warning` and above at default verbosity, so neither can print a summary at default verbosity. `getSummary()` returns the counts for tests; `withManager()` starts a new summary.
- **Each scaffold is its own load.** The builder service is shared, and the fixtures executor clears the entity manager after every fixture, so `withManager()` calls `reset()` and forgets everything the previous scaffold declared; the service is also tagged `kernel.reset`. A second scaffold reaches the first one's content only through the lookups above: redeclaring a layout or page by reference keeps it, and `getRoute()` falls back to an existing route with that name. Components it adds to a group the first scaffold created are not created, as for any kept group. Carrying builder state across scaffolds held detached entities and failed on flush (#344). `Fixture\AppendTest` runs two scaffolds in one real `doctrine:fixtures:load`.

### `generate-fixtures` (#189, #321, #452)

`silverback:api-components:generate-fixtures` writes the scaffold a developer would write by hand, and it reloads as the same site. Two authorities: `tests/Functional/Fixture/GenerateFixturesRoundTripTest.php` builds a site, generates, purges, loads the generated file and compares (add a test for anything new the generator must carry), and **`tests/Functional/Fixture/scaffolds/SiteScaffold.php` is the style**: `test_a_scaffold_written_in_the_documented_style_generates_itself` loads it with a real `doctrine:fixtures:load` and regenerates it byte for byte, and `GenerateFixturesCommandTest::test_the_whole_file_for_the_documented_site` builds the same site in memory. Change that file and the generator together; php-cs-fixer excludes it.

- **Pipeline** (`src/Fixture/Generator/`): `Site\SiteReader` loads and orders the site into a `SiteSnapshot`, `Plan\ScaffoldPlanner` makes every decision (methods, names, scopes, values) into a `ScaffoldPlan`, `Code\ScaffoldRenderer` lays it out. The planner only coordinates, in this order: `MethodPlanner` (methods and their builder calls), `ExecutionOrder`, `ComponentPlacer` (one `ComponentPlan` per component, with `GroupPlanner` for groups and `PropertyValueWriter` for values), `ComponentScopeDecider` (local, property or inline, and hoisting), `DeclarationOrderer` (declarations, late assignments, draft links), then names. Everything they cannot express goes to the shared `NotReproducedReport`, so its messages keep that order. **The boundary:** the planner writes every builder call and argument as a PHP string (through `PhpValueExporter`, never raw `var_export()`, so a newline is escaped); the only thing it leaves to the renderer is how a component is referred to (`ScaffoldRenderer::expression()`: inline `new X()`, `$x` or `$this->x`), because names are given last. The `Plan` classes are data. `MethodKind` decides the builder call and the method name's suffix. `StoredFileExporter` writes the asset files and is built per run by `ScaffoldGenerator`, the service; the planner and its `EntityStateReader` (which caches fresh instances) are built per run too, so no service holds a site between runs. Test a decision in the class that makes it (`ComponentScopeDecider`, `DeclarationOrderer` and `ExecutionOrder` on hand-built plans), their interplay on the plan (`ScaffoldPlannerTest`), a layout on a hand-built plan (`ScaffoldRendererTest`).
- **Order is site-map order, so a reload generates the same file**: layouts by reference; pages routed by path, then routeless by reference, then templates; page data routed by path, then by title; children the same inside their parent; groups by reference; positions by `sortValue`; redirects after their target, then by path. Never iterate a repository result unsorted.
- **One private method per layout, top-level page and top-level page data, then `redirects()`**, called from `build()`. A child page or page data has its own method, called by one `->nested($this->childPage(...))` per child. Method names come from `Code\VariableNamer`, in file order.
- **A component used in more than one method is a typed property**, declared in the first method the builder **runs**, not the first in the file: `build()` order, then nested closures as `CwaFixtureBuilder::evaluateNested()` runs them, page data closures before page closures in each pass. `Plan\ExecutionOrder` mirrors that loop; change both together. Components related across methods are both properties, assigned in the later method.
- **A property first used in a nested method is declared in that method's top-level ancestor**, which always runs: an `--append` load never runs the closures of skipped page data, so a later method would read an uninitialised property. A component that owns groups stays in the nested method, next to the page it belongs to, unless that method is under page data, which an `--append` load may skip; then it moves to the top-level method with every component its groups declare there. The builder persists such a component after the closures, so moving it never creates it early.
- **A position, page data property or component field holding a draft of a published component is generated holding the published component** (#520), as a write would now store it, and reported once per holder kind (`ComponentPlacer::publishedInsteadOfDraft()`); such a state exists only in a database written before the rule. A draft is therefore only ever reached through its published component: it is declared right after it and linked with `$cwa->component($published)->draft($draft)`. A group a draft co-owns with its published component is generated once, on the published component; a group owned by the draft alone (only an older database) is reported.
- **A component is inline** (`new X()`, or `$cwa->publish(new X())`) only with one use and nothing to set, link, draft or own. A related component placed nowhere is declared before the one that refers to it; a cycle's back edge is assigned after every declaration of the method.
- **Names**: the first non-blank `label`, `title`, `name`, `heading` or `reference`, else the text of the first `<h1>`–`<h6>` in any string field (a tag or `&nbsp;` separates words), else the owner's reference and group name; a word repeated consecutively counts once (`trainingMainContainer`, never `trainingMainMainMain…`); up to 4 words, then the short class name. Leading numbers follow the first word (`results2024DummyNavigationLink`); numbers alone put the class first (`page404`). A clash gets `2`, `3`…, after an underscore when the name ends in a digit (`dummyNavigationLink2024_2`). A draft is its published component's name plus `Draft`, the published name is fitted 5 characters shorter so both share one stem, and a taken draft name is a clash on the pair (`live2`/`live2Draft`). **No identifier is over 40 characters**: stop words (`to`, `the`, `our`…) go first unless only stop words are left, then identifying words from the end, then the class name loses its leading words, never its last; a clash suffix counts. A name starting with the class lower-cases a leading acronym whole (`htmlBlock`). `make:cwa-scaffold` uses the same `VariableNamer`.
- **`PhpValueExporter` keeps every string byte-exact.** Never insert a newline that is not in the value: long HTML is split after top-level block closing tags into concatenated pieces, a value with newlines is a flexible nowdoc only when no line starts with a tab or ends in a space or tab (an editor or php-cs-fixer would strip it), it has no other control character and no line could close the marker (`HTML2`… otherwise), and anything with a control character is a double-quoted piece. Lists are written without keys (`array_is_list()`).
- **Arguments**: a group's `allow:` then `max:` (only when not null). A layout's and page's `uiComponent:` is named, since the bare suffix (`'Primary'`) does not say what it is.
- **Routes**: a route is always written as an explicit `route:`. A link is `->linkRoute('route', routeName: 'about')`, the second argument named so the call says it is a route name. `routeName:` and a redirect's `name:` are left out only when the builder would derive the same name; both sides use `Utility\RouteName::fromPath()`, and the redirect simulation makes the name unique against the site's routes and the redirects before it, as `CwaFixtureBuilder` does. A route association is `->linkRoute()` next to its component or page data; `afterRoutes()` is never generated. A page's or page data's own route that redirects is `->redirectTo(routeName: …)` after its `liveAt()` (#461); a target that is not part of the site is reported, never dropped (`test_no_route_redirect_is_left_out_without_being_reported`).
- **Dates**: a past `publishedAt` is `$cwa->publish($x)` (published at load time), a future one `publish($x, at: …)` exactly, and only a future or null `liveAt` is written. `--keep-timestamps` writes every one exactly. A draft is `$cwa->component($published)->draft($draft)`.
- Component and page data fields come from Doctrine metadata through `Site\EntityStateReader`, which reads through `initializeObject()` first (`getFieldValue()` does not initialise a lazy object), and skips identifiers, timestamps, the publishable fields, uploadable storage fields and values equal to the property default. Each is written through its public property, else its setter.
- **Stored files are exported under the name their reload is stored under, minus the token** (#452), so a second generation writes the same asset: `Utility\StoredFileName`, shared with `UploadableFileManager`, lowercases the slug and takes the extension from the content type (guessed from the content as `File::getMimeType()` does). A PHP temp name `phpGPCPOl` with PNG content is `phpgpcpol.png`. A clash with different content takes `-2`, `-3`…, which the slug keeps on reload. **Each distinct content is written once** (#469): `StoredFileExporter` keys what it wrote by SHA-256, so identical bytes return the name of their first export in site-map order and every `new File(...)` for them names one asset; `count()` is distinct files. A reload therefore stores the later resources under the first one's slug (and extension), which a second generation exports under the same name. Sharing one source is safe because `UploadableFileManager::persistFiles()` reads it through a stream and never moves it; keep it that way. Loaded back through `new File(...)`.
- **Fixture asset store (#462).** With `fixtures.assets` configured, or `--assets-store`/`--assets-dir` for one run, a stored file is written once to the store under its SHA-256 (no extension, directly under the prefix), listed in `<Class>.assets.json` beside the class (`FixtureAssetManifest::pathFor()`, the one place that names it, from the **class short name**, not the file name), and written as `$cwa->asset('<hash>')`; with **nothing configured the output is byte-for-byte what it was** (readable copies, `new File(...)`, no manifest), and the golden scaffold pins it. The class never says where files live: `FixtureAssetStoreFactory` decides it for both sides, `forGeneration()` (null means the readable mode) and `forLoading()` (unconfigured means `assets/` beside the class). `AbstractCwaScaffold::load()` hands the builder the manifest path from reflection. `Fixture\AssetStoreTest` round-trips every mode, and a real `doctrine:fixtures:load`, to a fixed point.
- **The manifest name is the name the reload stores**, so a fixed point needs the loader to pass it: `FixtureAssetLoader` returns a test-mode `UploadedFile` over a `tmpfile()` copy with the manifest name as the client name, which `UploadableFileManager::resolveOriginalName()` prefers. Never point it at the store file itself, and never `move()` it. The copies live as long as the loader's handles: the builder's `reset()` (each `withManager()`) closes them, so they outlive the flush that stores them. The same content under a second name is `$cwa->asset('<hash>', name: '…')`; the manifest keeps the first.
- **Only a hash-named file is an asset.** Store listing and pruning ignore anything else under the prefix (a README, the old readable copies), and never recurse. Generating into a **local** store deletes only what **the same scaffold's previous manifest** listed and the new one does not (read before it is overwritten), and keeps any hash another `*.assets.json` manifest in the same directory lists, so scaffolds can share a folder (#481, #489); an invalid previous or sibling manifest deletes nothing. A file no manifest of this scaffold listed is never deleted by generating, even if nothing names it. Only manifests beside the one being written are read, so scaffolds in different directories sharing a configured `fixtures.assets` path can still delete each other's hashes; `prune-fixture-assets` with every manifest is the way to clean such a store, and a storage error while it prunes exits 1 and lists what was already deleted, so the store's state is never a guess. A flysystem store is never pruned by generating. A read failure is reported as before; a store **write** failure fails the generation (not a `FilesystemException`, so the writer does not swallow it). The loader checks the copy's hash.
- **An IRI inside a field value is linked, never copied stale** (#452): `Plan\IriValueLinker` finds a string that is the IRI of a site page, layout, routed page data or route (top-level or at any key path of an array, with or without the import prefix, matched by stripping the first segment either side), writes `null` in its place and emits `->linkIri()`; a top-level IRI writes no assignment. Any other string that the IRI converter resolves to an item, or to a missing item, is reported and copied as it is. Collection IRIs (`/_/pages`) are plain strings.
- **Site config parameters are never exported**: they are per-environment configuration, not content (Daniel's decision). Do not add them, and do not report them as not reproduced.
- **Every file it writes fails the command when the write fails** (exit 1, naming the path): the class, the `<Class>.assets.json` manifest (then nothing is pruned) and each readable asset copy (`StoredFileExporter` throws, as a store write does). The output directory must already exist and be writable, checked before anything is generated, so nothing is exported for a class that cannot be written; it is never created. Check the return of every `file_put_contents()`, `mkdir()` and `rename()`.
- Imports go through `Code\ImportCollector`: two classes with one short name get a namespace-prefixed alias, never a duplicate `use`.
- **Anything it cannot express is listed in the command output** ("could not be reproduced"), never exported approximately: a group owned by a draft alone, a position, page data property or component field holding a draft of a published component (generated holding the published component), a group shared without a location reference, a page data position's fallback, a route or entity outside the site, an IRI it cannot link, a value the exporter cannot write, a redirect that is not live (a fixture redirect always is). A message that would repeat identically per entity (no setter, not writable as PHP, a collection) is one line per class and field with a count, through `NotReproducedReport::addForEach()`; a message naming an IRI, file or group stays individual.
- Field defaults are compared with a fresh instance when the class can be built with no arguments, so a value the constructor overrides is still written; otherwise with the declared default. A scaffold that silently drops content is worse than one that says so.
- The `make:cwa-scaffold` skeleton is written in the same style, around the template's `App\Entity\NavigationLink` (`--link-class`). The link is written only when that class exists, is a component, and has a writable `label` (a public, non-readonly property without `private(set)`, else `setLabel()`, which the skeleton then calls) and `route` (asked for interactively, noted otherwise), and published only when it is publishable, so the skeleton always loads. `MakeCwaScaffoldTest` loads the rendered skeleton through a real `CwaFixtureBuilder` for each kind of link class and for none.

> **The bundle strips mapped superclasses from its JOINED roots' discriminator maps** (#323). `AbstractComponent` and `AbstractPageData` declare no discriminator map, so Doctrine's `addDefaultDiscriminatorMap()` includes every subclass the driver knows, including an application's `#[ORM\MappedSuperclass]` base, which has no table. `MappedSuperclassDiscriminatorMapListener` runs on `loadClassMetadata`, which Doctrine dispatches after building the default map, and removes those classes from `discriminatorMap` and `subClasses`. It detects a mapped superclass the way Doctrine's own `peekIfIsMappedSuperclass()` does: it loads the candidate through the mapping driver into a fresh `ClassMetadata`. That works for every driver and never goes back through the metadata factory, which would recurse into the root still being loaded. `isTransient()` cannot tell them apart, because it is false for both entities and mapped superclasses. Abstract `#[ORM\Entity]` bases have tables and stay in the map. `AbstractDummyAppComponent` is a mapped superclass so the round-trip feature covers this.
